# raceemu

ウマ娘レースエミュレータ（https://mee1080.github.io/umasim/race/）の調査と、それをもとにした改良版 Web アプリである。

本家の計算モデルを TypeScript に移植したうえで、並列実行、統計、設定どうしの比較、目標からの逆算、スキルの組み合わせ探索を載せてある。
計算はブラウザの Worker で回るので、サーバを立てなくても動く。

[ワークフロー](.github/workflows/image.yml)が `main` への取り込みごとに `ghcr.io/promodeler314-a11y/raceemu` を更新するので、`kubectl apply -f deploy/k8s.yaml` で置く。

詳しくは[配信](docs/deploy.md)を参照。

ビルドした成果物は静的ファイルだけで動くので（[配信](docs/deploy.md)の 1 節）置き場は選ばないが、画面の読み取りと個体の保存はサーバのある版でしか使えない。

`main` と pull request では[検査のワークフロー](.github/workflows/ci.yml)が `typecheck`、`test`、`build`、`e2e` を通す。

## 画面

- **設定**：ステータス、コース、脚質、やる気、バ場状態、キャラ、所持スキル、デバフ、実行オプション。補正後の値とコース形状を併せて出す。固有と進化はキャラから取る。ウマ娘詳細画面の写真から、所持スキルとステータス・適性を取り込める（サーバを立てた版のみ）。
- **結果**：平均タイム、完走率、最速と最遅、ゴール時の残り体力、タイムの分布、スキル別の発動状況。発動条件を確率で近似しているスキルには印を付ける。
- **比較**：保存したスナップショットを列に並べる。基準の列を選べて、差のある項目だけに畳める。分布を重ねられる。
- **詳細**：1 レースの速度と体力の推移と、スキル発動やフェーズ境界を拾ったイベント一覧。図にはスキルの発動位置を縦線と印で出し、カーソルを寄せるとスキル名が読める。
- **勝率**：出走する全頭を同時に走らせる。相手 1 頭ずつにステータスとスキルを持たせ、着順の分布と勝率を出す。相手には保存した個体をそのまま当てられる。
- **探索**：目標から必要なステータスを求める逆算と、スキルポイントの予算内で最良の組み合わせを探す探索。逆算は、位置取り調整が何回起きた場合かを分けて出せる。組み合わせ探索の候補は、いま選んでいるスキルからでも、育成計画（育成ウマ娘とデッキと継承）からでも作れる。

設定とスナップショットは IndexedDB に残る。
設定は URL のハッシュに載せて共有できる。
ライトとダークを切り替えられる。

ステータスとスキル構成の組（個体）は、サーバのある版ならヘッダの「個体として保存」でサーバ側に残る。
勝率の面で相手に割り当てるための材料である。

## 開発

```
pnpm install
pnpm test        # 本家との突き合わせとスキル条件の網羅。24 ファイル 201 件
pnpm typecheck
pnpm sim --count 1000 --location 10006 --course 10606
pnpm bench --count 10000       # 並列実行の実測
pnpm dev                       # UI の開発サーバ
pnpm build                     # UI のビルド
pnpm e2e                       # ビルドした UI を実際のブラウザで確認
pnpm monotonicity --trials 60  # 逆算の前提（単調性）の検査
pnpm optimize --budget 600 --style SEN  # 組み合わせ探索の実測
pnpm plan --chara スペシャルウィーク --budget 600  # 育成計画からの探索の実測
pnpm run multi --trials 500    # 全頭同時に走らせたときの挙動の実測（multi は pnpm の下位コマンドと衝突するので run を挟む）
pnpm order-field --trials 200  # 順位条件の判定が相手の作り方でどう変わるかの実測
pnpm fetch-tessdata            # 画面の読み取りに使う学習データ（35 MB）
pnpm e2e:import                # 画面の読み取りをサーバとブラウザで確認
pnpm api                       # サーバ側の口（apps/api）
```

`pnpm test` の 201 件のうち 13 件は手元の材料に依る。
学習データを取っていなければ読み取りの 7 件が飛び、実機の写真を置いた場所を `RACEEMU_REAL_SCREENSHOT_DIR` で指していなければステータス読み取りの 6 件が飛ぶ。
写真はゲームの著作物なのでリポジトリに置いていない。

## 構成

`packages/sim` が計算モデル、`packages/data` がコースとスキルとサポートカードと育成ウマ娘のデータ、`packages/solver` が逆算と探索、`apps/web` が UI、`apps/api` がサーバ側の口である。
`apps/api` は探索のほかに、画面の読み取り（`/api/ocr/*`）と個体の保存（`/api/individuals`）を持ち、静的ファイルも同じオリジンから配る。
`deploy/` に Dockerfile と Kubernetes のマニフェストを、`design/` に画面モックを置いてある。
計算モデルは [mee1080/umasim](https://github.com/mee1080/umasim) からの移植であり、本リポジトリも AGPL v3 とする。
ゲームのデータ（`packages/data/assets/`）は週次の[ワークフロー](.github/workflows/sync-game-data.yml)が本家を追いかけ、新しいウマ娘やスキルが増えていれば下書き PR を出す（[詳細](docs/m1-report.md#7-データを本家に追随させる)）。

## M10 の後

回として分けていないぶんである。実機で使ってみて出た穴を埋める作業が多い。

- **読み取りを文字認識から画像分類に替えた。** 本物の「ウマ娘詳細」画面では、丸いアイコンと装飾つきの背景が隣の文字を巻き込んで壊す。二値化（[読み取り](docs/ocr-design.md)の 5 節）で組み立てた見本は 21/21 まで上がったが実機は直らず、umacapture（MIT）の学習済みモデルを借りて行ごとの分類で解く形にした。実機 1 枚で 23 件すべてを当てる（同 6 節）。
- **ステータスと適性も読む。** 同じ画面の上半分を切り出す。適性の記号は文字認識に向かないので色相で読む。実機 3 枚 45 か所すべて一致した（同 7 節）。
- **スキル・コースデータを本家に追随させた。** M1 の抽出から一度も更新していなかった。週次のワークフローが取り直し、差分があれば下書き PR を出す。
- **個体をサーバに保存できるようにした。** ステータスとスキル構成だけを持ち、レース結果は持たない。勝率の面で相手に当てる材料である（[サーバ側の設計](docs/server-design.md)）。
- **詳細の図にスキルの発動位置を出した。** 図とイベント表を見比べなくても、どこで発動したのかが分かる。
- **逆算を位置取り調整の回数ごとに出せるようにした。** 逆算が返す最小値は調整をほとんど払わない走りを前提にしており、実戦との差が 170 から 210 ほど出る（[逆算と探索の設計](docs/solver-design.md)の 2.2.1 節）。
- **組み合わせ探索を全 Worker に散らした。** 1 回の評価が 1 塊に収まって 1 Worker しか働いていなかった。同じ結果のまま 109.5 秒から 69.6 秒になった（[M7](docs/m7-report.md)の 6 節）。
- **組み合わせ探索を育成計画から始められるようにした。** 候補を取り込んだスキル表からではなく、育成ウマ娘とデッキと継承から組み立てる。汎用の白は継承でいくらでも足せるのでスキルポイントだけが縛り、固有の継承版は 6 つまでしか積めない。レース前に値が決まる条件で先に落とすので、買える 1784 個は東京 芝2400m の先行で 999 個になる（[逆算と探索の設計](docs/solver-design.md)の 7 節）。
- **順位条件の判定を既定で入れた。** M6 で入れた最大の精度改善が既定で切られていたため、初めて使う人は本家と同じ「順位条件は満たしている前提」の甘い評価を見ていた。探索もこの設定に従うので、過大評価を突く状態が既定になっていた（[逆算と探索の設計](docs/solver-design.md)の 4 節）。束の作り方を直したあとでなければ入れられないものだったので、[順位条件の判定を実戦に近づける](docs/order-field.md)の 7 節の 1、2、4 が入るのを待って入れた。**相手の想定はまだ固定の弱い側（同節の 3 番目）なので、強い個体では後ろ寄りの条件がほとんど発動しない。**
- **本家と設定をやり取りできるようにした。** キャラ名、ステータス 5 つ、適性 3 つ、スキル名を並べた 1 行である。本家で作った設定を持ち込んで勝率や逆算に掛けられる。区切りは改行でもタブでもよく、引き当てられなかった語は捨てずに知らせる（`apps/web/src/transfer.ts`）。
- **実行前に所要時間を出すようにした。** 試行回数は単騎で 20 万、全頭同時で 5 万まで指定でき、押してから数十分かかる設定が作れる。直前の実測から見込みを出す（[M10 の後の方針](docs/roadmap.md)の 4.2 節）。
- **サブパスと、JSON でない応答の扱いを直した。** 末尾の `/` が無い URL で真っ白になる件と、口の無い版が返す HTML を JSON として読もうとして落ちる件である（[配信](docs/deploy.md)の 1 節）。

いちばん重要なのは `needs-measurement` である。

バ身の換算と順位率の対応表もスキルデータの注記からの読み取りであって、実測ではない。
この 3 つ（[#51](https://github.com/promodeler314-a11y/raceemu/issues/51)、
[#52](https://github.com/promodeler314-a11y/raceemu/issues/52)、
[#53](https://github.com/promodeler314-a11y/raceemu/issues/53)）が決まらないあいだ、
順位条件まわりの精度は誰にも分からない。**コードを書く作業ではなく、ゲームを遊んで数字を取る作業である。**

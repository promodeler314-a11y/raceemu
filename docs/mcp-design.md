# MCP サーバーとして使う設計

エミュレータを、Claude Code や Claude Desktop から道具として呼べるようにする。
ゲーム画面のスクリーンショットを渡して「ロンシャン 2400 m の不良で予想して」と頼めば、勝率と予想印が返ってくる、という使い方である。

## 1. なぜ MCP にするのか

画面を開かなくても、会話の中で同じ問いに答えられるようにしたい。
実際に会話の中でやってみると、計算そのものは既存の部品で足りた。
手間がかかったのは、計算の前後を手作りでつなぐところだった。

- 画像から読んだスキル名を、スキル ID に直す。名前の揺れ（`〜` と `～`、`涛` と `濤`）を直し、同じ名前の固有・継承版・進化版から正しいものを選ぶ。
- 競馬場とコースの ID を探す。ロンシャンの 2400 m が `10201` の `11203` だと知るのに、データを引く必要があった。
- 出走表を `RaceSetting` に組む。適性は距離・バ場・脚質ごとに 1 つだけ選んで渡す。脚質が決まっていなければ決める。
- 全頭同時のレースを回して、勝率・連対率・複勝率を集計する。
- 集計から予想印を付ける。

これらを道具として固定すれば、手作りのつなぎを毎回書かずに済み、同じ入力なら同じ答えが返る。

**計算は新しく書かない。** 既存の `runMultiRace` と `WorkerPool` と `OrderTally` を呼ぶ薄い包みにする。
新しく書くのは、名前の解決と、出走表の組み立てと、印の付け方である。

## 2. 形

### 2.1 stdio の 1 プロセス

接続は標準入出力（stdio）とする。
`apps/mcp` を新設し、クライアントがプロセスを起動して JSON-RPC をやり取りする。
HTTP で配ることは、いまは考えない。認証の設計が要るためである。

[サーバ側の設計](server-design.md)の 2 節と同じ理由で、**`apps/api` には依存しない。**
`apps/api` が落ちていても動き、静的配信だけの版とも無関係でいられる。
計算には自前の `WorkerPool` を `nodeWorkerFactory` で作って使う。

- 起動は `pnpm -s mcp`（`tsx apps/mcp/src/main.ts`）とする。**`-s` は省けない。** `pnpm mcp` は標準出力に `> raceemu@ mcp ...` というヘッダを出し、クライアントが接続を切る。実際に試して確かめた。
- **標準出力は JSON-RPC 専用である。** ログは標準エラー出力に書く。`console.log` が 1 行でも混ざると、クライアントが接続を切る。
- Worker の出力も標準出力に出さない。Worker は標準出力と標準エラー出力の両方を、親の標準エラー出力へ向ける（`createNodeWorkerFactory`）。
- **リポジトリの外からは、pnpm を介さない。** `pnpm --dir` で場所を指しても、corepack が起動した場所の `packageManager` を見て別の版を取りに行き、落ちる。`node` で `tsx` の CLI を絶対パスで呼ぶ。

クライアントの設定は、起動する場所によって 2 通りになる。

Claude Code は、プロジェクトの中で起動するので、`.mcp.json` に pnpm で書ける。

```json
{
  "mcpServers": {
    "raceemu": {
      "command": "pnpm",
      "args": ["-s", "mcp"]
    }
  }
}
```

Claude Desktop など、場所を選べないクライアントは、絶対パスで書く。

```json
{
  "mcpServers": {
    "raceemu": {
      "command": "node",
      "args": [
        "/path/to/raceemu/node_modules/tsx/dist/cli.mjs",
        "/path/to/raceemu/apps/mcp/src/main.ts"
      ]
    }
  }
}
```

どちらも `apps/mcp/test/stdio.test.ts` が、実際に起動して標準出力の全行が JSON であることを確かめている。

### 2.2 同時に 1 本だけ回す

1 回の呼び出しが数十秒から数分かかる。
複数の呼び出しを同時に回すと、Worker を取り合って全部が遅くなる。

- 計算を回す道具は、プロセスの中で 1 本ずつ順に処理する。待っている呼び出しがあれば、待たせる。
- 並列数は `os.availableParallelism()` に任せる。cgroup の読み取り（[`apps/api/src/config.ts`](../apps/api/src/config.ts)）は、手元で動かす stdio では要らない。
- 引き受ける試行数には上限を置く。既定は 1000 試行、上限は 20000 試行とする。頭数は 2 から 18 までである。

### 2.3 進捗と中断

MCP の `progressToken` が渡されていれば、`WorkerPool` の `onProgress(done, total)` をそのまま `notifications/progress` に流す。
クライアントが中断したときは、`AbortSignal` を `WorkerPool` に渡して Worker を止める。
`keepPartial` は使わない。途中までの集計を結果として返すと、試行数が少ないまま答えとして読まれるためである。

## 3. 道具

最初に作る道具は 9 つである。
どれも入力の検証に失敗したときは、何が足りないかを文章で返す。

| 道具 | 役目 |
| --- | --- |
| `check_lineup` | 出走表を計算せずに点検し、スキルの解決結果と警告を返す（3.7 節） |
| `win_rate` | 出走表とコースから、勝率・連対率・複勝率と予想印を返す |
| `skill_gain` | スキルを足したときの獲得バ身を、共通乱数のペア比較で返す |
| `find_skills` | スキル名から ID と種別と費用を引く |
| `list_courses` | 競馬場とコースの ID を引く |
| `data_info` | データの取得日と件数、計算の版を返す |
| `save_individual` | 書き起こした個体を保存する（3.8 節） |
| `list_individuals` | 保存した個体の一覧を返す |
| `delete_individual` | 保存した個体を消す |

次の道具は、需要が出てから足す。

- `compare`：設定どうしの比較
- `optimize`：スキルの組み合わせ探索
- `plan`：育成計画からの探索

### 3.1 出走表の形

画像に写っているものに近い形にする。
**適性は全部渡してよい。** 使うのは、コースの距離とバ場と、決めた脚質のものだけである。
画像から書き起こす側が「どれを使うか」を考えずに済む。

```json
{
  "name": "エルコンドルパサー",
  "chara": "[エル☆Número 1]エルコンドルパサー",
  "status": { "speed": 1222, "stamina": 913, "power": 871, "guts": 603, "wisdom": 831 },
  "statusRank": { "speed": "U", "stamina": "A+", "power": "A", "guts": "B", "wisdom": "A" },
  "aptitude": {
    "surface": { "turf": "A", "dirt": "B" },
    "distance": { "short": "F", "mile": "A", "mid": "S", "long": "B" },
    "style": { "nige": "E", "sen": "A", "sasi": "A", "oi": "C" }
  },
  "unique": { "name": "プランチャ☆ガナドール", "level": 6 },
  "skills": ["恵福バルカローレ", "あっぱれ大盤振る舞い！", "王手"],
  "style": "sen",
  "rating": 19409,
  "condition": "BEST"
}
```

- `name`、`status`、`aptitude`、`skills` は必須である。
- `statusRank` は画像のランク文字である。**省いてよいが、画像から書き起こすときは付ける。** 数値の読み違いを `check_lineup` が突き合わせて見つけるのに使う（3.7 節）。計算には使わない。
- `unique` の `level` は画像の `Lv` である。固有が写っていないときは省く。
- `chara` は固有スキルを引くのに使う。`[勝負服]ウマ娘名` の形でも、ウマ娘名だけでもよい。ウマ娘名だけで複数の勝負服が当たるときは、曖昧として返す。
- `style` を省くと、適性が最も高い脚質を採る。同じランクが並ぶときは、その脚質向けのスキル（`先行直線◎` など）の数が多いほうを採る。それでも並ぶときは、先行、差し、追込、逃げの順に採る。
- `rating`（評価点）は人気の既定を決めるのに使う。評価点の高い順に 1 から振る。どの頭にも `rating` が無ければ、入力の順に振る。
- `condition` の既定は `BEST` である。
- 枠番は指定しない。試行ごとに空いている枠から配る（`assignGates`）。

コースは次のとおりである。

```json
{ "track": { "location": 10201, "course": 11203, "condition": 4 }, "trials": 2000, "seed": 1 }
```

- `condition` は 1 が良、2 が稍重、3 が重、4 が不良である。
- 季節・天候・時刻は、指定がなければ画面の既定値（春、晴、ナイターではない）にする。省くと本家と同じ「満たしている前提」になり、春夏秋冬のスキルが同時に発動するので、必ず値を入れる（`TrackRef` の注記、[solver-design.md](solver-design.md) の 8 節）。**馬場状態を不良にしても、天候は雨にならない。** 雨を再現したいときは別に指定する。
- `seed` の既定は 1 とする。**画面の既定と同じ値にしてあるので、同じ出走表を画面に入れると同じ数値になる。**

### 3.2 スキル名の解決

スキル名から ID を引く規則を、道具の中に固定する。
この規則は、会話の中でやってみて決まったものである。

1. 名前は `normalizeSkillName`（`packages/data/src/skill-match.ts`）で揃えて、完全一致で引く。
2. 同じ名前が複数あるときは、次の順に選ぶ。
   - 進化、金、白、継承、特別、シナリオの順。
   - **固有は、出走表の `unique` に書かれたもので、`chara` が持ち主のときだけ固有として採る。**
   - 他のウマ娘の固有スキルは、継承版（`rarity: inherit`）を採る。継承版が無いものは、解決できなかったものとして返す。
3. 完全一致しなかったものは**自動では採らない。** 近い候補を付けて、解決できなかったものとして返す。
4. 同じスキルが 2 回あれば、1 つに畳む。畳んだことは警告として返す。同じスキルを 2 つ持つことはないので、画像のつなぎ目で行が重なった（3.7 節）と読める。

解決できなかったものがあるときの扱いは、`skip_unresolved` で決める。

- 既定（`false`）は、**計算を回さずに**、解決できなかった名前と近い候補を返す。呼び出した側が名前を直して、もう一度呼ぶ。
- `true` のときは、解決できなかったものを落として回す。応答に、何を落としたかを必ず載せる。

名前の近似一致で勝手に採らないのは、短い名前が 1 文字違いで別のスキルに当たるためである（[ocr-design.md](ocr-design.md) の 2 節と 3 節）。
画像を読み間違えたまま黙って別のスキルを走らせると、結果が静かに狂う。

**データに無いスキルがある。** 他のウマ娘に効くデバフ（`逃げけん制`、`追込ためらい`、`先行ためらい` など）は、スキルデータに載っていない。
これらは解決できなかったものとして返り、`skip_unresolved` で落とすと、効果は計算に入らない。
このことは応答の `notes` に必ず書く（4.2 節）。

### 3.3 `win_rate`

出走表（2 頭から 18 頭）とコースを受け取り、全頭同時のレースを回して集計する。
計算は画面の「全頭同時」と同じである。`runMultiRace` を試行のぶんだけ回し、`OrderTally` で集計する。

応答は、頭ごとに次を持つ。

- 勝率、連対率（2 着以内）、複勝率（3 着以内）、平均着順、平均タイム
- 勝率の標準誤差 `sqrt(p (1 - p) / n)`
- 採った脚質と人気、解決したスキルの一覧
- 予想印

**採った値は全部返す。** 脚質を既定で決めたとき、人気を評価点から振ったとき、距離適性にどれを使ったかを、応答に書く。
入力に書かなかった値は、返ってきて初めて呼び出した側が気付けるためである。

### 3.4 予想印

印はシミュレーションが返すものではない。
勝率の順位から、次の規則で付ける。

| 印 | 規則 |
| --- | --- |
| ◎ | 勝率 1 位 |
| ○ | 勝率 2 位 |
| ▲ | 勝率 3 位 |
| △ | 勝率 4 位と 5 位 |
| ☆ | 6 位以下で、勝率が最も高く、かつ 3 % 以上の 1 頭 |
| 無印 | それ以外 |

**差が小さいときは、印の順位を断言しない。** 隣り合う順位の勝率の差が、差の標準誤差（2 頭それぞれの標準誤差の二乗和の平方根）の 2 倍以内なら、応答に「接戦」の注記を付ける。見るのは 6 位までの隣り合う組（1-2 位から 5-6 位）だけで、両方とも勝率 0 の組は見ない。6 位は ☆ の候補で、△ との境目が印に関わるためである。
会話の中でやったときも、3 番手以下は乱数の種を変えると順位が入れ替わった。
印の規則は、勝率の順位だけを見るので、注記がその限界を補う。

### 3.5 `skill_gain`

1 頭の出走表と、足したいスキルの一覧を受け取り、足したときの獲得バ身を返す。

- 足す前と足した後を、同じ試行番号どうしで引き算する。共通乱数のペア比較である（[設計の土台](../CLAUDE.md)）。
- 順位条件は、相手の分布を自分と同格に作ったフィールドに対して判定する（`defaultFieldProfile`）。
- 獲得バ身は、タイム差に基準の終端速度を掛けて、1 バ身 = 2.5 m で割る。**1 バ身の換算は、ゲームでの実測が無い**（`packages/sim/src/data/constants.ts` の `bashinMeters`）。応答の `notes` に書く。
- 結果は平均と標準誤差で返す。

### 3.6 `find_skills`、`list_courses`、`data_info`

- `find_skills`：名前の一覧を受け取り、3.2 節の規則で引いた結果を返す。`win_rate` を回さずに、名前だけを確かめるために使う。
- `list_courses`：競馬場名、距離、バ場で絞って、競馬場 ID とコース ID を返す。
- `data_info`：スキルの件数、データの取得日、計算の版を返す。

### 3.7 画像から取り込む

育成ウマ娘の詳細画面の画像をチャットに貼って、そのまま出走表にして走らせたい。
**読み取りは Claude が行い、サーバーは画像を受け取らない**（6 節）。
サーバーが受け持つのは、読み取りの誤りに気付き、会話の中で直せるようにすることである。

**書き起こす範囲は、スキルだけではない。** 画面に写っている次のものをすべて読む。

- 名前（`[勝負服]ウマ娘名`）と、ウマ娘評価点
- ステータス 5 つの数値と、ランク文字
- 適性 10 項目（バ場 2、距離 4、脚質 4）。**使うコースで 1 つに絞らず、全部書く。** 保存した個体を別のコースで使えるようにするためである。
- 固有スキルと、その `Lv`
- 所持スキルの全部

やる気は画面に写らないので、読まない。`condition` の既定（`BEST`）か、利用者の指定を使う。

流れは次のとおりである。

1. 利用者が画像を貼る。1 枚に 1 頭で、何枚でもよい。
2. Claude が画像を出走表（3.1 節）に書き起こす。
3. Claude が `check_lineup` を呼ぶ。**計算は回さず**、解決結果と警告だけが返る。数秒で終わる。
4. 警告があれば、Claude が画像を見直して直し、もう一度 `check_lineup` を呼ぶ。
5. Claude が読み取り結果を表にして、利用者に確かめてもらう。
6. 保存してよいか聞き、よければ `save_individual` を呼ぶ（3.8 節）。保存は利用者の確認が取れてからにする。
7. `win_rate` を呼ぶ。数分かかりうる計算の前に、読み取りの誤りを潰しておくための順序である。

`check_lineup` は頭ごとに次を返す。

- 入力したスキル名と、採ったスキルの対応。入力の順に並べ、画像と見比べられるようにする。
- 解決できなかった名前と、近い候補。
- 採ったスキルの数。画像の下が切れていないかを、利用者が画面の数と比べられる。
- 採った脚質と、その理由。
- 警告。次のものを見る。
  - 同じスキルが 2 回ある（畳んだ）。
  - **同じグループのスキルを 2 つ持っている。** `右回り○` と `右回り◎` のように、上位と下位は同時に持てない。読み違いの疑いが強い。
  - 固有スキルが見つからない、または持ち主が違う。
  - ステータスが 1 から 2000 の外にある。
  - **ステータスの数値とランク文字が合わない。** 画像には `B 628` のように両方が写っているので、書き起こすときに文字も渡してもらい、突き合わせる。数字の読み違いは、スキル名と違って辞書で捕まえられない。

ランクの対応は、会話の中で読んだ 11 頭ぶんの画像から、次のように見た。100 刻みである。
画像に写っていたのは S までなので、**検査するのは C 以上 S 以下に限る。**
`S` を超える数値（1100 以上）は、ランク文字が `S` でなければ（`U` 系など）よしとして、細かくは見ない。
C 未満は、画像に無かったので検査しない。

| ランク | C | C+ | B | B+ | A | A+ | S |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 範囲 | 400 台 | 500 台 | 600 台 | 700 台 | 800 台 | 900 台 | 1000 台 |

読み取りの注意は、**サーバーの `instructions`（`initialize` で返す説明）と、道具の説明文に書く。**
どちらも常に Claude の文脈に載るので、読み取りの規則を別の場所に置いて読み忘れることがない。
書く内容は次のとおりである。

- 固有スキルは、虹色の枠の先頭の行で、右端の `Lv` が固有レベルである。
- スキルの色（金、桃）は種別の手掛かりに使わない。種別は名前から引く。
- 読み違えやすい字は、`〜` と `～`、`涛` と `濤`、`ヘ` と `へ`、`迸` と `送` である。`○` と `◎` は別のスキルなので、取り違えない。
- 縦に長い画面を 2 枚つないだ画像では、つなぎ目の行が重なる。重なった行は 1 つにする。
- 下が切れて見えない行があれば、推測せず、利用者に聞く。
- 他馬に効くデバフ（赤い札のスキル）はデータに無い。名前はそのまま書き、解決できなかったと返ってきたら、利用者に落としてよいか確かめる。

### 3.8 個体の保存

読み取った個体を保存しておき、あとの会話で名前を指すだけで出走表に使えるようにする。
毎回画像を貼り直さずに済み、読み取りの手間と誤りの機会が 1 度で済む。

**保存するのは、書き起こした個体であって、画像ではない。**
画像はゲームの画面なので、保管しない。持つのは次のものである。

| 項目 | 中身 |
| --- | --- |
| `id` | 個体の識別子（UUID） |
| `label` | 呼び名。省くと `chara` から作る。同じ呼び名を複数持てる |
| `runner` | 3.1 節の出走表の形。**適性は全部持つ** |
| `skillIds` | 解決したスキルの ID。名前の一覧も `runner` に残す |
| `createdAt`、`updatedAt` | 保存と更新の日時 |

**既存の `apps/api` の保存先とは別にする。**
`apps/api` の `IndividualStore`（`/api/individuals`）が持つのは、コース用に絞ったステータスとスキル ID である（`UmaStatus` と `skillIds`）。
距離・バ場・脚質の適性を 1 つずつしか持たないので、別のコースでは使えない。
ここで持ちたいのは全部の適性を含む個体なので、形が合わない。

- 保存先は SQLite（`node:sqlite`）の `mcp-individuals.db` とする。`apps/api` が使う `individuals.db` とはファイルを分けるので、同じディレクトリを指しても衝突しない。
- ディレクトリは環境変数 `RACEEMU_MCP_DATA_DIR` で指す。既定は `~/.raceemu` とする。
- **`apps/api` の個体と相互に使えるようにするのは、いまはしない。** 画面側の個体は絞った形なので、MCP の個体から画面の個体へは、コースを指定して変換できる。逆は適性が足りない。変換は必要になってから足す。

道具は次のとおりである。

- `save_individual`：3.1 節の出走表の形と呼び名を受け取る。**`check_lineup` と同じ点検を通す。** 解決できなかった名前が残っていれば保存しない。ステータスとランク文字が合わない警告は、保存を止めず、応答に載せる。
- `list_individuals`：呼び名の一部で絞って、一覧を返す。頭ごとに呼び名、ウマ娘名、ステータス、スキル数、保存日時を持つ。
- `delete_individual`：`id` を指定して消す。**取り消せない操作なので、道具の注記で破壊的な操作と宣言する**（MCP の `destructiveHint`）。Claude は利用者に確かめてから呼ぶ。

同じ個体を二重に保存しない。
**ウマ娘名、ステータス 5 つ、固有 `Lv` が全部同じものは、同じ個体とみなして上書きする。** 応答に `updated: true` を付ける。
スキルを足した育成の途中経過を、貼り直しのたびに別の個体として増やさないためである。
ステータスが 1 つでも違えば別の個体として保存する。

保存した個体は、`win_rate` と `check_lineup` の出走表で、全項目の代わりに指せる。

```json
{ "individual": "エルコンドルパサー", "style": "sasi" }
```

- `individual` は `id`、または呼び名である。呼び名が複数に当たるときは、候補を返して止まる。
- 脚質と `condition` は、その場で上書きできる。ステータスやスキルの上書きはできない。違う個体にしたいなら、保存し直す。
- **保存した個体を使うとき、スキルの解決結果が保存したときと同じかを見る。** 名前で引き直すので、データの取り直しで同じ名前に新しい版が増えると、採るスキルが変わりうる。黙って変わると、同じ個体の結果が変わった理由が分からなくなる。違えば `individual_changed` の警告を返す。ID がデータから消えたときも、この警告になる。
- `individual` の引き方は、`id` の完全一致、呼び名の完全一致、呼び名とウマ娘名の部分一致の順で、当たった段で止める。

## 4. 応答

### 4.1 構造化した JSON と、読める文章

MCP の応答は、構造化した JSON（`structuredContent`）と、読める文章（`content`）の両方を返す。
文章は Markdown の表である。JSON を読めないクライアントでも、そのまま見せられるようにする。

### 4.2 `notes` に必ず書くこと

次のことは、応答の `notes` に毎回載せる。
結果だけが 1 人歩きして、前提が落ちるのを防ぐためである。

- 順位や接触の判定は、ゲームと突き合わせていない（`needs-measurement`）。
- 解決できず、落としたスキル。
- 使ったデータの取得日と、その後に追加されたウマ娘やスキルが入っていない可能性。
- 他馬に効くデバフが入っていないこと。出走表にデバフを持つ頭がいるとき。

## 5. データの鮮度

`packages/data/assets/` は週次の取り直しなので、新しいウマ娘やスキルが入っていない期間がある。
会話の中でも、黒ルドルフのスキルが入っておらず、本家から取り直す必要があった。

- `packages/data/scripts/sync-game-data.py` が、取り直した日を `packages/data/assets/meta.json` に書く。`data_info` はこれを読む。`assets` は手で編集しない決まりなので、このファイルも手では書かない。

`meta.json` は次の 3 つを持つ。

| 項目 | 中身 |
| --- | --- |
| `syncedAt` | データが最後に変わった日（UTC、`YYYY-MM-DD`） |
| `digest` | `skills`、`courses`、`supports`、`charas` の 4 ファイルの SHA-256 |
| `source` | 出どころ（`https://github.com/mee1080/umasim`） |

**書き直すのは、指紋が変わったときだけである。**
毎回日付を書くと、データが変わっていない週も `git diff` に差が出る。
ワークフローは `git diff --quiet -- packages/data/assets` で PR の要否を決めているので、毎週 PR が出てしまう。
そのため `syncedAt` は「最後に確かめた日」ではなく「最後に変わった日」を意味する。
最後に確かめた日はどこにも残らないので、`data_info` は「この日以降の追加は入っていない可能性がある」と書く。

**指紋は改行を LF にそろえてから求める。**
手元の Windows は `autocrlf` で CRLF になっており、そろえないと CI（Linux）と値が違ってしまう。
`packages/data/test/meta.test.ts` が TypeScript 側で同じ手順で求め、`meta.json` の指紋と一致することを見張る。
データだけを直して `meta.json` を直し忘れると、このテストが落ちる。

`meta.json` が無いところから始めるときは、取得せずに書くモードを一度だけ使う。

```
python3 packages/data/scripts/sync-game-data.py --meta-only --date 2026-09-21
```

日付は、データを最後に取り直したコミットの日にした（2026-09-21）。
- 環境変数 `RACEEMU_ASSETS_DIR` で、別の場所の `assets` を指せる。新しいデータを試すために使う。
- 出走表のスキルが未収録で解決できなかったときは、データが古いことを疑う文を添える。

## 6. 入れないもの

- **画面の読み取り（OCR）。** Claude が画像を直接読めるので要らない。学習データ 35 MB を配ることにもなる。読み取りの誤りを会話の中で直せるようにする仕組みは 3.7 節に置く。
- **画像の保管。** 保存するのは書き起こした個体だけで、画像は持たない（3.8 節）。
- **HTTP と認証。** 1 節のとおり、いまは考えない。
- **他馬へのデバフの計算。** データが無く、決め打ちにする根拠もない（[race-emulator-analysis.md](race-emulator-analysis.md) の 8 節）。
- **単騎でのタイム分布。** `pnpm sim` で足りる。必要になったら `compare` に含める。

## 7. 作る順序

1. `sync-game-data.py` に `meta.json` を書かせる。
2. スキル名の解決（3.2 節）を `packages/data` に切り出してテストする。
3. 出走表から `RaceSetting` を組む部分（3.1 節）を `packages/sim/src/multi` に置く。画面の `buildSetting` と二重になるが、画面側の置き換えは別の回にする。
4. `apps/mcp` に MCP の殻を作る。依存は `@modelcontextprotocol/sdk`（MIT）と、その入力検査に使う `zod` である。`apps/*` は workspace に入っていないので、どちらもルートの `package.json` に足す。依存を足すので `pnpm-lock.yaml` が変わり、CI の `pnpm install --frozen-lockfile` も通す。
5. 道具を 1 つずつ足す。順序は `data_info`、`list_courses`、`find_skills`、`check_lineup`、`win_rate`、`skill_gain` とする。
6. 個体の保存（3.8 節）を足す。順序は `save_individual`、`list_individuals`、出走表で `individual` を指せるようにすること、`delete_individual` とする。保存は `win_rate` が動いてから足す。保存した個体を使う先が無いうちは、検査もできないためである。

## 8. 検査

- **計算が直接の呼び出しと一致する。** `win_rate` の結果が、同じ乱数の種で `runMultiRace` と `OrderTally` を直接呼んだ値と、1 ビットも違わない。
- **スキル名の解決。** 名前の揺れ（`〜` と `～`、`涛` と `濤`）、同名の固有・継承版・進化版の選び分け、解決できなかった名前が候補付きで返ること。
- **印の規則。** 勝率の並びを与えて、印と「接戦」の注記が決まる。乱数は使わない。
- **MCP の往復。** SDK のメモリ上の通信路で、`tools/list` と各道具の呼び出しを通す。
- **標準出力が汚れていない。** 子プロセスとして起動し、`initialize` から `win_rate` までを呼んで、標準出力のすべての行が JSON であることを確かめる。ここが崩れると、クライアントが黙って接続を切る。
- **中断。** 回している途中で中断して、Worker が止まり、次の呼び出しが通ること。
- **点検（`check_lineup`）。** 同じスキルの重複を畳む、同じグループの 2 つを警告する、ステータスとランク文字の食い違いを警告する、未解決の名前が候補付きで返ること。ランクの表の境目（599 と 600、799 と 800、999 と 1000）も確かめる。
- **個体の保存。** 保存して一覧に出る、同じ個体は上書きされて数が増えない、ステータスが 1 つ違えば別の個体になる、未解決の名前が残っていれば保存されない、`id` と呼び名の両方で出走表に指せる、呼び名が複数に当たるときは止まる、プロセスを起動し直しても残る。
- **会話で使った出走表。** 11 頭の出走表を固定して、乱数の種を決めて回し、◎と○が変わらないことを確かめる。値そのものは固定しない（計算の変更で動くため）。

## 9. 決めていないこと

- **`rating` が無いときの人気。** 入力の順に振るのが妥当かどうかは、人気を使う条件が実際にどれだけ効くかを測ってから決める。
- **印の `☆` の規則。** 3 % という閾値は、会話の中の 1 つの出走表から決めた。別の出走表で見直す。
- **ランクの対応表。** 100 刻みという表（3.7 節）は、画像 11 枚から読んだもので、ゲームの仕様と突き合わせていない。画像に無かった C 未満と S 超の呼び名は、特に未確認である。食い違いは警告にとどめ、拒否はしない。
- **保存先の既定。** `~/.raceemu` は仮の値である。リポジトリの中に置くと、個体が git に載りうるので避けた。
- **画面の個体との共有。** 3.8 節のとおり、いまはしない。共有したくなったら、コースを指定した変換を足す。
- **Worker の出力の向き先。** Worker の標準出力と標準エラー出力は、親の標準エラー出力へ向けている（`createNodeWorkerFactory`）。実際のプロセスで `win_rate` まで通して標準出力が JSON だけであることは確かめたが、Worker が実際に何かを出力した場合の挙動は試していない（いまの Worker は何も出力しない）。
- **試行数の上限。** 20000 は仮の値である。会話の中で測ったとき、11 頭の 1 試行は 1 スレッドで 100 から 140 ms かかった。並列数が少ない環境では 20000 試行に数十分かかりうる。`WorkerPool` で実測してから決める。

# M6 の結果

[順位条件の扱い](order-condition.md)で決めたフィールド軌跡モデルを実装した。
順位条件を実際に判定できるようになり、これまで「満たしている前提」で扱っていたぶんの歪みが数字で見えるようになった。

## 1. 順位率の対応表

順位率の条件から該当順位への対応は、本家のスキルデータの注記から組み立てる。
手で写すと写し間違いが混ざるので、生成する。

```
python3 packages/data/scripts/build-order-rate-table.py \
  packages/data/assets/skills.json packages/sim/src/data/orderRate.ts
```

このスクリプトは、単一の境界を示す注記と範囲を示す注記の両方から境界を取り出し、矛盾があれば止まる。
実際に使われている 22 通りの条件（出現 1431 回）がすべて埋まることも確かめている。
生成された表は 9 頭立てと 12 頭立てだけを持つ。
それ以外の頭数の条件に当たったら、従来どおり満たしている前提に落として記録する。

## 2. フィールドの作り方

相手 N-1 頭それぞれについて、普通にレースを回して位置の時系列を取る。
相手は自分の影響を受けず、相手同士も干渉しない。
そのぶんフィールドは自分の構成に依存しないので、あらかじめ作って使い回せる。

```
フィールド 64 本 × 相手 8 頭を 1689 ms で生成
1 本あたり 1785 フレーム、束全体で 7.2 MB
```

束は Worker には送らない。
数 MB を塊のたびに転送することになるうえ、指定（相手の想定、コース、シード、本数）が同じなら同じ束になる。
そこで**指定だけを送り、Worker 側で作ってキャッシュする**。
生成に 1.7 秒かかるので、塊ごとに作り直すと計算時間を上回る。

実行時にすることは位置の比較だけである。
毎フレーム、自分より前にいる相手の数を数えて 1 を足せば順位になる。
比較は多くても 18 回で済む。

試行番号から束の 1 本を選ぶので、同じ試行番号なら同じフィールドが選ばれる。
[逆算と組み合わせ探索の設計](solver-design.md)の共通乱数によるペア比較が、フィールドを含めて成立する。

## 3. 何が変わったか

これが M6 の眼目である。
同じ構成を、順位条件を無視した場合とフィールドを入れた場合で走らせ、スキルの発動率を比べた。
東京芝2400、9 頭立て、2000 試行。

| 脚質 | スキル（順位条件） | 順位を無視 | フィールドあり |
| --- | --- | ---: | ---: |
| 逃げ | 真骨頂（後方寄り） | 89.5 % | **0.0 %** |
| 逃げ | 正攻法（前半分） | 88.9 % | 88.9 % |
| 先行 | 真骨頂（後方寄り） | 89.5 % | 35.8 % |
| 差し | 正攻法（前半分） | 88.9 % | 49.0 % |
| 追込 | 正攻法（前半分） | 88.9 % | **5.1 %** |
| 追込 | 順風満帆（前半分） | 90.1 % | 3.2 % |

**脚質と噛み合わない条件のスキルは、80 ポイント以上も過大に評価されていた。**
逃げが後方寄りの条件を満たすことはこのモデルでは起こらないのに、9 割発動する扱いになっていた。

同時に、これが単なる脚質の関門になっていないことも見える。
先行の 35.8 パーセントと差しの 49.0 パーセントは、レースごとに順位が動いた結果である。

## 4. 順位が脚質でほぼ決まってしまう

実装してみて分かった限界を書いておく。

脚質だけを変えてゴール時の順位を集めると、次のようになる（相手は共通の想定、300 試行）。

| 脚質 | 1 位 | 2 位 | 3 位 | 4 位 | 5 位以下 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 逃げ | 35 % | 28 % | 18 % | 11 % | 6 % |
| 先行 | 74 % | 19 % | 5 % | 1 % | 1 % |
| 差し | 1 % | 5 % | 12 % | 33 % | 49 % |
| 追込 | 0 % | 1 % | 7 % | 20 % | 72 % |

差しと追込がほとんど勝てない。
理由は、**このモデルでは 1 頭あたりのタイムのばらつきが小さすぎる**ことにある。
同じステータスで脚質だけ変えたときの平均タイムは 118.4 秒から 118.9 秒に収まるのに、同一脚質内の標準偏差は 0.18 秒しかない。
脚質の差が標準偏差の 3 倍近くあるため、順位はほぼ決まってしまう。

実際のレースなら、差しが序盤に遅いのは後ろにいるからであり、前が飛ばせば前も苦しくなる。
このモデルでは全頭が独立に自分のレースを走るので、その相互作用が無い。
[順位条件の扱い](order-condition.md)の 6 節に「相手が自分に反応しない」と書いた限界が、順位の分散が小さいという形で出ている。

これは相手の想定を変えても解決しない。
モデルの側の性質だからである。
[順位条件の扱い](order-condition.md)で L3 として置いた自己整合フィールド（フィールドを自分の走りの分布に近づける反復）が要る理由が、ここではっきりした。

**当面の使い方としては、同じ脚質の中で構成を比べるぶんには問題がない。**
偏りは候補すべてに共通に乗るためである。
脚質をまたいで比べるときは、この偏りを承知しておく必要がある。

## 5. 実装していない条件

- **順位帯の維持**（`order_rate_inNN_continue` など、43 回）：順位の履歴を持てば判定できる。まだ入れていない。
- **距離差**（先頭との距離、前後との距離、123 回）：位置の差からは求まるが、条件の値がどの単位なのかを確かめていない。[順位条件の扱い](order-condition.md)の 7 節の検証項目のままである。当てずっぽうの換算で実装するより、無視のままにしておくほうが害が小さい。
- **内外の位置**（28 回）：相手のレーンを持っていないので判定できない。

順位そのものと順位率で、順位に関わる条件の出現 1875 回のうち 1724 回（92 パーセント）を占める。

## 6. 確認したこと

- 対応表の主要な項目が[順位条件の扱い](order-condition.md)の表と一致する。
- 順位が 1 から出走頭数の範囲に収まり、前に出るほど上がる。
- 同じ試行番号なら同じフィールドを引く。
- 逃げに後方寄り条件のスキルを持たせると、順位を無視したときは 8 割以上発動し、フィールドを入れると 1 割未満に落ちる。
- ブラウザでも同じことが起きる（`pnpm e2e` に組み込んだ。90.8 パーセントから 0 パーセントへ）。

## 7. 次にやること

M7 の組み合わせ探索に進む。
順位条件を判定できるようになったので、[逆算と組み合わせ探索の設計](solver-design.md)の 4 節で懸念した「探索がモデルの過大評価を突く」度合いは、少なくとも順位については小さくなった。
探索を回す際は、フィールドを入れた状態を既定にする。

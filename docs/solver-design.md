# 逆算と組み合わせ探索の設計

[改良版の設計](webapp-design.md)に、二つの探索機能を追加する。
どちらもシミュレータを繰り返し呼ぶ上位の層であり、計算モデルそのものには手を入れない。

- **逆算**：「最大スパートを 8 割の確率で決めるにはスタミナがいくつ要るか」のように、目標を先に決めて必要なステータスを求める。
- **組み合わせ探索**：候補として挙げたスキルの中から、スキルポイントの予算内で期待タイムが最も縮む組み合わせを探す。

どちらも、乱数を含む関数の値を頼りに探索する問題である。
先に、その扱いを二つの機能で共通の土台として決める。

## 1. ノイズの中で差を見るための土台

### 1.1 共通乱数と、乱数ストリームの分離

二つの設定を比べるとき、別々の乱数で走らせると、差のほとんどがシミュレーションのばらつきに埋もれる。
そこで**同じ乱数を両方に使い、試行ごとの差を取る**。
これは共通乱数法と呼ばれる分散減少の常法であり[^crn]、本アプリの探索はこれを前提に組む。

ところが、単一の乱数列を頭から消費する実装では、共通乱数が成立しない。
スキルを 1 つ足すと、そのスキルの発動抽選が乱数を 1 個余分に引き、以降のすべての乱数がずれてしまう。
「同じ乱数」のつもりが、実際には無関係な 2 本の乱数列を比べることになる。

したがって、**乱数源を用途ごとに独立したストリームに分ける**。

```ts
// 用途ごとに別の生成器を持ち、種は (baseSeed, trial, streamId) から決める
const rng = {
  startDelay:   stream(seed, trial, Stream.StartDelay),
  temptation:   stream(seed, trial, Stream.Temptation),
  sectionSpeed: stream(seed, trial, Stream.SectionSpeed),
  skillLot:     (skillId: string) => stream(seed, trial, Stream.SkillLot, skillId),
  // 以下、下り坂、位置取り調整、追い比べ、レーン移動、ランダム区間 ...
};
```

スキルごとの抽選は、スキル ID をストリームの識別子に混ぜる。
こうすると、あるスキルを足しても他のスキルの抽選結果は変わらない。
出遅れ、掛かり、区間乱数といったレース側の乱数も、スキル構成に影響されずに固定される。

この設計は探索の精度を決める中核であり、後から差し込むのは難しい。
[改良版の設計](webapp-design.md)の M1 で乱数を実装する時点で、この分離を入れておく必要がある。

### 1.2 逐次的な打ち切り

候補を比べるたびに毎回 1 万試行を回すのは無駄である。
差が大きい候補は少ない試行で決着し、差が小さい候補にだけ試行が要る。

そこで、ペア差分の平均と標準誤差を試行しながら更新し、次のいずれかで打ち切る。

- 信頼区間が 0 を跨がなくなった：優劣が付いたので打ち切る。
- 信頼区間が実用上の無差別幅（既定 0.01 秒）に収まった：差が小さすぎるので同着として打ち切る。
- 試行数が上限に達した：判定を保留して次へ進む。

複数候補を同時に扱う場面では、段階的に試行数を増やしながら見込みのない候補を落とす方式を使う[^sh]。
少ない試行で全候補をふるいにかけ、生き残った候補にだけ試行を追加する。

### 1.3 計算予算とアンタイム性

探索の所要時間は、候補数と試行数の積で決まり、簡単に分単位になる。
そこで、**利用者が指定するのは試行回数ではなく計算予算（秒数、または総試行数）**とする。

探索は途中経過を常に持ち、いつ止めても、その時点での最良解と信頼区間を返せる形にする。
進捗表示には、消化した予算、現在の最良解、二番手との差の信頼区間を出す。

## 2. スタミナの逆算

### 2.1 目標の定義

「必要なスタミナ」は目標の定義によって変わるため、何を満たしたいのかを選ばせる。

- **最大スパート率**：終盤突入時に最高速度で押し切れると判定される割合。既定の目標はこれにする。
- **完走率**：ゴール時点で体力が尽きていない割合。
- **残り体力**：ゴール時の残り体力の下側分位点が 0 以上。

いずれも「達成率 p パーセント」という形で指定する。
最大スパート率 80 パーセントと 95 パーセントでは必要なスタミナが大きく変わるため、単一の答えではなく後述の曲線として見せる。

### 2.2 試行ごとの臨界値を求める

素朴な方法は、スタミナを二分探索し、各点で N 回試行して達成率を測ることである。
しかしこれは、達成率という一つの数字しか得られないうえ、その数字自体が二項分布のばらつきを持つ。

代わりに、**試行ごとの臨界スタミナを求める**。

乱数ストリームを分離したので、1 つの試行（1 つのシード）の中では、スタミナ以外の乱数はすべて固定されている。
その試行における「最大スパートが成立する最小のスタミナ」は、二分探索で 11 回ほどシミュレーションすれば求まる。
これを N 試行ぶん集めると、臨界スタミナの分布そのものが手に入る。

```
達成率 p を満たす必要スタミナ = 臨界スタミナの p 分位点
```

計算量は素朴な方法と同じ（N 掛ける 11 回程度）でありながら、得られる情報が違う。
達成率を任意の p について読める曲線が 1 回の実行で出るため、「80 パーセントなら 1150、95 パーセントなら 1320」という形で提示できる。
分布の形も見えるので、二山になっている（ある確率で掛かるかどうかが結果を二分している、など）ことに気付ける。

### 2.3 単調性という前提

この方法は、**1 試行の中でスタミナを増やしたとき、達成が単調に変わる**ことを前提にしている。
スタミナが増えれば体力に余裕が生まれ、スパートが伸びるという方向は自然である。

ただし、この前提が破れうる箇所は実際にある。
持久力温存と位置取り調整は、必要体力と現在体力の比較で分岐する。
スタミナが増えたせいで位置取り調整に入り、体力を使ってしまう経路がありうる。

そこで、実装時に単調性を検査する。
数百通りの設定について、スタミナを細かく動かしながら達成の有無を記録し、反転が起きる頻度と幅を測る。
反転がごく稀で幅も小さければ二分探索を使い、無視できない頻度で起きるなら、臨界値の探索を粗い全走査に切り替える（探索範囲を刻んで最小の達成点を取る）。
どちらを採るかは M5 の最初の作業で決める。

### 2.4 逆算の対象を広げる

同じ枠組みは、スタミナ以外にも使える。
根性、スピード、パワーの各ステータス、そして回復スキルの総回復量が対象になる。

- 単調性が期待できるものだけを対象にする。
- 目標も、達成率だけでなく「平均タイムが t 秒を切る」に一般化できる。

## 3. スキル組み合わせの探索

### 3.1 問題の形

候補スキルの集合から部分集合を選び、スキルポイントの予算内で目的関数を最大化する。

```
maximize   E[基準タイム] - E[タイム(S)]        S ⊆ 候補
subject to cost(S) ≤ 予算
```

目的関数は平均タイムの短縮を既定とし、上位 2 割の平均（引きが良かったときの伸び）と下位 2 割の平均（下振れの底上げ）にも切り替えられるようにする。
どれを選ぶかで最適な構成は変わるため、単一の答えを押し付けない。

### 3.2 コストの構造

スキルポイントの計算は単純な足し算にならない。

- 上位スキルの表示ポイントには、同じグループの下位スキル分が含まれている。すでに下位を取っているなら、追加コストはその差分である。
- ヒントレベルによって必要ポイントが割り引かれる。本家の係数表はレベル 0 から 5 に対して 1.0、0.9、0.8、0.7、0.65、0.6 である。
- 同じグループから複数を取ることはできない。

したがって、**コストは「すでに何を持っているか」に依存する**。
探索の内部では、スキルを個別の要素ではなく、グループ単位の選択（そのグループから何も取らない、下位を取る、上位を取る）として扱う。
これでグループ内の排他性と差分コストが自然に表現できる。

### 3.3 単体の貢献度だけでは決まらない

スキルは互いに独立ではない。

速度上昇スキルが同じ区間に重なれば、目標速度は加算されるものの、加速が追い付かず効果を出し切れない（本家が「速度上昇無効割合」として集計している現象である）。
回復スキルは、体力に余裕がある構成では回復量が上限を超えて捨てられる。
逆に、加速スキルと速度スキルが噛み合って伸びる組み合わせもある。

そのため、単体の貢献度を足し合わせた値は、実際の組み合わせの価値と一致しない。
単体の貢献度は探索の出発点としては有用だが、最終的な比較は必ず組み合わせ全体をシミュレートして行う。

### 3.4 探索の手順

1. **単体評価**：各候補を単独で加えたときの短縮量を、少ない試行数で測る。ポイント当たりの効率で並べる。
2. **貪欲な初期解**：効率の高い順に、予算に収まる範囲で採用して初期解を作る。
3. **局所探索**：初期解に対して、1 つ追加する、1 つ外す、1 つを別のものに入れ替える、という近傍を試す。共通乱数によるペア差分で比較し、有意に改善するときだけ移動する。
4. **多点開始**：初期解を貪欲法だけに頼らず、乱択で作った複数の初期解からも走らせ、最良を採る。
5. **仕上げ**：得られた上位の解について、試行数を増やして順位を確定させる。

分枝限定法のような厳密解法は採らない。
単体貢献度の和が上界になる保証がなく、探索木を安全に刈れないためである。
これはヒューリスティックであり、最適解であることは保証しないと明示する。

### 3.5 評価予算の配分

段階ごとに、1 候補あたりの試行数を変える。

| 段階 | 候補数の目安 | 1 候補あたりの試行数 |
| --- | --- | --- |
| 単体評価 | 数十 | 少ない（数百） |
| 局所探索 | 数百から数千 | 中程度（逐次打ち切り） |
| 仕上げ | 上位数個 | 多い（数千から 1 万） |

Worker への投入単位は「1 候補と 1 つのシード範囲」とし、往復の回数を抑える。
局所探索は逐次的な判断が続くため、近傍を 1 つずつ評価するのではなく、近傍をまとめて投入して結果が返った順に判断する。

### 3.6 結果の見せ方

単一の答えだけを出すと、僅差の別解が見えず、乱数由来の順位変動を最適解と誤読させる。

- **上位の解を並べる**：短縮量と信頼区間を付けて上位 10 件ほどを表示し、最良解との差が有意かどうかを示す。
- **採用頻度**：上位の解の中で各スキルが何回選ばれたかを出す。ほぼ常に選ばれるスキルと、入れ替わりが激しいスキルを区別できる。
- **予算曲線**：予算を変えながら探索し、ポイントと短縮量のパレート曲線を描く。「あと 100 ポイントでどれだけ縮むか」が読める。
- **構成の内訳**：選ばれた解について、各スキルの発動率と発動位置を通常の詳細表示につなぐ。

## 4. 最適化はモデルの誤差を突く

ここまでの機能には、避けられない性質がある。
**探索は、モデルが実際より高く評価している箇所を選び出す**。

本家の解析で見たとおり、順位に関する条件は「満たしている前提」として無視され、進路ブロックや追い抜きは固定の確率で近似されている。
効果値のうち確認しようのない部分は最大値前提で固定されている。
人手で構成を組むときは、これらを承知のうえで割り引いて読める。
探索器は割り引かない。
順位条件だけが厳しい強力なスキルは、モデル上は無条件で発動するため、探索の上位に必ず現れる。

この歪みを消すことはできないが、見えるようにはできる。

- 解に含まれるスキルのうち、無視された条件や近似条件に依存するものに印を付け、依存度の高い解には警告を出す。
- 近似確率を上下に振った設定でも同じ解が選ばれるかを確認する感度分析を用意する。順位や接触に敏感な解は、そこで順位が入れ替わる。
- 目的関数の内訳として、近似条件に依存するスキルの寄与分を分離して表示する。

利用者に対しては、出力を「この条件下でモデルが最も高く評価した構成」として提示する。
実戦での最適構成だと称さない。

## 5. アーキテクチャへの影響

```
packages/sim      計算モデル。乱数ストリームを外から受け取る形にする。
packages/solver   逆算と組み合わせ探索。sim を呼ぶが、UI には依存しない。
apps/web          UI。solver に計算予算と設定を渡し、途中経過を受け取る。
```

`packages/sim` に必要な変更は次の二点である。

- **乱数ストリームの分離**：1.1 節のとおり。M1 の設計に含める。
- **一括評価の入口**：設定とシード範囲を受け取り、フレーム列を作らずに集計値だけを返す関数を公開する。探索はこれしか呼ばない。

`packages/solver` は Worker プールを占有する。
UI からの通常のシミュレーション実行と同時には走らせず、実行中は片方を待たせる。

## 6. 段取りの見直し

[改良版の設計](webapp-design.md)の段取りに、次の二つを追加する。
M5 に一括りにしていた発展項目を分割する形になる。

- **M5 逆算**：単調性の検証、臨界値探索、分布と曲線の表示。M2 の並列実行が前提である。
- **M6 フィールド軌跡モデル**：順位条件を判定できるようにする。[順位条件の扱い](order-condition.md)を参照。
- **M7 組み合わせ探索**：単体評価、貪欲法、局所探索、逐次打ち切り、結果の提示、感度分析。M5 で作る逐次打ち切りの仕組みを共有する。

探索を順位条件の実装より後に置くのは、順序の都合ではなく結果の質の問題である。
順位条件を満たす前提のまま探索を回すと、4 節で述べた歪みが最も強く出る構成が上位に並ぶ。
それを一度出してしまうと、後から順位条件を入れたときに解が入れ替わり、どちらを信じるべきかがわからなくなる。
先に順位を実装しておけば、探索の出力は最初から一貫する。

M1 の内容にも変更が入る。
乱数ストリームの分離は、後から入れると本家との一致確認をやり直すことになるため、最初から含める。

## 7. 未決の論点

- **単調性が破れた場合の扱い**：2.3 節の検査結果によっては、臨界値探索を全走査に切り替える。計算量が数倍になるため、探索範囲の刻み幅を含めて M5 で決める。
- **目的関数の既定値**：平均タイムを既定にするか、下位 2 割の平均（安定性）を既定にするかは、使い方次第である。両方を並べて表示し、既定は使ってから決める。
- **候補スキル数の上限**：局所探索の近傍サイズは候補数の二乗で効くため、候補が百を超えると仕上げまで到達しない可能性がある。上限を設けるか、単体評価で足切りするかを M6 で決める。
- **計算予算の既定値**：実測前なので決められない。M2 で 1 試行あたりの所要時間を測ってから設定する。

[^crn]: 同一の乱数列を複数の設定に適用して差の分散を下げる手法。モンテカルロシミュレーションにおける分散減少法の一つである。
[^sh]: successive halving。候補全体に少ない予算を配り、成績下位を切り捨てて残りに予算を再配分することを繰り返す。

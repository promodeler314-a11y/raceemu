# レースエミュレータ改良版の設計

本書は、[mee1080/umasim のレースエミュレータ](race-emulator-analysis.md)の計算モデルを土台に、UI と可視化を作り直し、試行回数を桁で増やせる Web アプリを新規実装するための設計である。

**本書は着手前に書いたものである。** 以後の回で線引きが動いた箇所には、その旨を添えてある。
いま何が残っているかは [issue](https://github.com/promodeler314-a11y/raceemu/issues) が持つ。

## 1. 何を作り、何を作らないか

改良の主眼は二つに絞る。

- **可視化と操作性**：速度、体力、スキル発動、コース形状を同一の時間軸で読める図を用意し、設定同士を横に並べて比較できるようにする。
- **計算速度と規模**：Web Worker で並列化し、既定 100 回という試行回数の制約を取り払う。1 万回規模を待たされずに回せる状態を目標にする。

次の二つは、今回の対象外とする。

- **複数頭の同時シミュレーション**：他馬を実体として持つ改造は、順位条件、進路ブロック、隊列によるペース変動をすべて作り直すことになり、規模が一桁違う。単騎モデルと確率近似は本家の方式をそのまま踏襲する。
  → **この線引きは後で外した。** [M6](m6-report.md) で他馬の位置を時系列として持つフィールド軌跡モデルを入れ、
  [M9](m9-report.md) で全頭を同時に走らせる勝率の面を入れた。進路ブロックは確率近似のままである
  （[順位条件の扱い](order-condition.md)の 6 節）。
- **モデル精度そのものの改良**：未実装や暫定のまま残っている係数（全開スパートの速度上限、ブロック時の減速など）は、実測データとの突き合わせが前提になる。今回は本家と同じ挙動を再現することを正しさの基準とし、係数の改良は将来の課題として切り離す。

この線引きの結果、**本アプリの計算結果は本家と統計的に一致していなければならない**。
一致を確認する手段は 7 節で述べる。

**この基準は単騎モデルについては今も生きている**（`packages/sim/test/reference.test.ts`）。
一方、順位条件を判定する経路は本家に対応するものが無いので、突き合わせる相手はゲームそのものになる。
そちらは未了である（[#51](https://github.com/promodeler314-a11y/raceemu/issues/51)）。

## 2. ライセンス上の前提

本家 umasim は AGPL v3 で公開されている。
計算モデルをそのソースから読み取って移植する以上、成果物は派生著作物として扱うのが安全な解釈になる。
AGPL v3 はネットワーク越しに利用させる場合にもソース提供義務を課すため、静的ページとして配信するだけでも、利用者がソースを取得できる状態にしておく必要がある。

したがって、本アプリも AGPL v3 で公開し、リポジトリへのリンクを画面上に置く前提で設計する。
これを避けたい場合は、本家のソースを参照せずゲーム側の観測だけから独立に実装し直すことになるが、その道は本設計の範囲外である。

## 3. 技術構成

```
apps/web        React + TypeScript の UI。Vite でビルドする。
packages/sim    計算モデル。DOM に依存しない純粋な TypeScript。
packages/data   コースデータとスキルデータ、およびその型とローダ。
```

- **ビルド**：Vite。静的配信を想定する（[配信](deploy.md)）。
- **UI**：React 18 と TypeScript。状態管理は Zustand を使い、設定オブジェクトを 1 つのストアに集約する。
- **スタイル**：Tailwind CSS。設定項目が多いため、密度の高いレイアウトを短く書けることを優先する。
- **グラフ**：uPlot。1 レースあたり数千点の系列を複数重ねるため、描画コストの低さで選ぶ。ヒストグラムなど点数の少ない図は自前の SVG で足りる。
- **テスト**：Vitest。計算モデルの回帰テストが中心になる。

`packages/sim` を UI から完全に切り離すのは、Worker にそのまま載せるためであり、後述する Node 上での検証を可能にするためでもある。

## 4. 計算モデルの移植方針

### 4.1 乱数をシード可能にする

本家はグローバルな乱数を直接呼ぶため、同じ設定でも結果を再現できない。
本アプリでは**シード付きの疑似乱数生成器を明示的に引き回す**。

```ts
interface Rng { nextDouble(): number; nextInt(maxExclusive: number): number; }
function createRng(seed: number): Rng;   // sfc32 など、状態の小さい高速な生成器
```

試行 `i` のシードは `hash(baseSeed, i)` で決める。
これにより、結果表から気になった 1 本を選び、そのシードでフレーム単位の再生ができる。
本家では 1 回目の試行しか詳細を見られなかった部分が、任意の試行に広がる。

さらに、**乱数源を用途ごとに独立したストリームへ分ける**。
単一の列を頭から消費すると、スキルを 1 つ足しただけで以降のすべての乱数がずれ、二つの設定を同じ乱数で比較できなくなる。
出遅れ、掛かり、区間乱数、スキルごとの発動抽選をそれぞれ別のストリームにし、種を `(baseSeed, trial, streamId)` から導く。
この分離は後から入れると本家との一致確認をやり直すことになるため、M1 に含める。
理由と使い道は[逆算と組み合わせ探索の設計](solver-design.md)の 1.1 節で述べる。

### 4.2 設定と状態の型

Worker との受け渡しは構造化クローンで済ませたいので、設定はプレーンなオブジェクトに保つ。

```ts
type SimulationInput = {
  uma: UmaStatus;          // ステータス、脚質、適性、やる気、枠番
  track: TrackRef;         // レース場、コース、バ場状態、出走人数
  skills: string[];        // スキル ID の配列
  debuffs: Record<DebuffType, number>;
  options: SimulationOptions;  // ポジションキープ、発動率固定、ランダム区間、システム係数
  seed: number;
};
```

派生値（補正後ステータス、最大体力、各フェーズの基準速度など）は、入力から 1 回だけ計算して `DerivedSetting` に固める。
本家が Kotlin の遅延初期化で行っていることを、明示的な前処理として書く。

### 4.3 スキル条件の事前コンパイル

本家と同じく、レース開始時に各スキルの条件式を関数へ変換する。
レース前に確定する条件は真偽値に潰し、毎フレーム評価する条件だけをクロージャとして残す。
ランダム発動区間も開始時に確定させる。

この方針は速度のために不可欠である。
条件データを毎フレーム解釈すると、1 レースあたり数千フレーム掛ける所持スキル数の解釈コストがそのまま乗る。

### 4.4 ホットループの書き方

フレームループは 1 秒あたり 15 回、1 レースで千数百回、1 万試行で 1500 万回まわる。
ここでの割り当てを減らすことが速度を決める。

- レース状態は 1 つの可変オブジェクトに持ち、フレームごとに新しいオブジェクトを作らない。
- 発動中スキルの配列は使い回し、要素の削除は末尾との入れ替えで行う。
- 統計だけが要る試行では、フレーム列を記録しない。記録は詳細表示を要求された試行に限る。
- 集計対象の結果は数値の組にすぎないので、`Float64Array` に詰めて Worker から転送する。

## 5. 並列化の設計

```
UI スレッド ── SimulationController ──┬── Worker 1 (packages/sim)
                                      ├── Worker 2
                                      └── Worker N   N = hardwareConcurrency - 1
```

- Worker は常駐させ、実行のたびに立ち上げ直さない。探索は同じ設定を少しずつ変えて何千回も評価するため、起動とデータ読み込みが計算時間を上回る（[M2 の結果](m2-report.md)の 2 節）。
- 試行を固定サイズのチャンク（既定 256 試行）に割り、空いた Worker へ順に配る。
- 各 Worker は自分のチャンクの結果を `Float64Array` にまとめ、転送可能オブジェクトとして返す。
- 進捗はチャンク完了ごとに UI へ通知する。UI 側では 100 ミリ秒程度に間引いて再描画する。
- 実行中に設定を変えたら、走っている実行を中断して投げ直す。Worker には中断フラグをチャンク境界で見せる。
- Worker が使えない環境では、同じ関数を UI スレッドで小分けに実行する経路を残す。

各試行は完全に独立しており、共有する状態は入力と読み取り専用のデータだけである。
そのため `SharedArrayBuffer` は使わず、構造化クローンと転送だけで組む。
これはクロスオリジン分離の設定を要求しないという利点もある。

試行回数の上限は UI 側で決め打ちにせず、実測した 1 試行あたりの所要時間から「この設定なら 1 万回で約 n 秒」と見積もりを表示する。
目標は 2000 m 級のコースで 1 万試行を数秒に収めることだが、確定した数字ではないので、最初のマイルストーンで実測して設計に反映する。

## 6. 画面と可視化

### 6.1 画面構成

画面の骨格は[モック](../design/README.md)を正とする。
本節はその要点だけを述べる。
モックと現在の実装の差は[モックと実装のズレ](ui-gap.md)にある。

広い画面では設定と結果を左右に分ける。
設定側は幅を固定し、結果側が残りを取る。
結果を見ているあいだ設定側は要約レールに畳み、何を設定したかだけが分かる状態にする。

ヘッダに **設定／結果／比較／詳細** の区切りを置く。
設定項目とグラフの量に対して 1 本のスクロールは長すぎるためである。

各区分の中身は次のとおりである。

1. **設定**：ウマ娘、コース、キャラ、スキル、デバフ、実行オプション。
2. **実行**：試行回数、シード、実行ボタン、進捗、所要時間の見積もり。
3. **結果**：平均タイムを主数字に置き、分布、最大スパート率、完走率、残り体力、スキルごとの発動状況を続ける。
4. **比較**：保存したスナップショットを列として並べ、差のある項目だけを出す。
5. **詳細**：1 本のレースについてのフレームグラフとイベント一覧。

**固有と進化はキャラから取り、スキルの一覧には出さない。**
本家がそうしている（`compose/.../race/SkillInput.kt` の `notUniqueSkills`）。
固有はキャラが持つものであって、一覧から拾ってくるものではない。
一覧に混ぜると、誰の固有なのかが画面に出ないまま別のキャラの固有を同時に持ててしまう。
固有とその継承版は名前が同じで 266 組あり、一覧から固有を外すと名前の衝突も消える。
キャラを変えたときに前のキャラの固有と進化を落とすこと、同じ名前の継承版を落とすこと、
固有レベルをキャラの側に置くことも本家と同じである。

[逆算](solver-design.md)と[組み合わせ探索](solver-design.md)は M5 と M7 で足した機能であり、モックには描かれていない。
どの区分に置くかは未決である（[モックと実装のズレ](ui-gap.md)の 1 節）。

フッタには、計算モデルの出所と AGPL v3 とリポジトリへのリンクを常に置く。
2 節で述べたとおり、これは体裁ではなくライセンス上の要求である。

### 6.2 本家から変える点

- **タイムの分布を出す**：平均と最速と最遅の 3 値ではなく、ヒストグラムと分位点を出す。設定変更が分布のどこを動かしたのかが見えるようにする。
- **コース形状を軸に重ねる**：グラフの背景に坂、コーナー、直線、フェーズ境界を敷く。スキルの発動位置が坂やコーナーとどう噛み合っているかを、数字を突き合わせずに読めるようにする。ただし 6.4 のとおり、量の違う系列を 1 つの縦軸に重ねることはしない。
- **スキル発動位置の分布**：全試行を通じた発動位置のヒストグラムを、スキルごとに小さく並べる。本家が持つ「平均発動位置」だけでは、二山になっている場合を見落とす。
- **任意の試行を再生する**：シードを保持しているので、分布の外れ値をクリックしてその 1 本の中身を開ける。
- **設定の並列比較**：本家は履歴を切り替えて見る形だが、列として横に並べ、差のある項目だけを強調する。
- **URL 共有**：設定をバイナリに詰めて base64url でハッシュに載せる。スキル ID の配列が支配的なので、可変長整数と差分符号化で十分に短くなる見込みである。
- **モバイル対応**：設定は 1 カラムに畳み、グラフは横スクロールと二本指ズームに対応させる。

### 6.3 近似の表示

本家の美点は、近似している箇所を利用者に開示している点にある。
これは引き継ぐ。
条件が近似で判定されたスキル、無視された条件を持つスキル、最大値前提で計算された効果には、結果表の中でその場に印を出す。

この印はまだ実装していない（10 節）。

### 6.4 二つの縦軸を 1 つの図に重ねない

速度と体力は単位も桁も違う。
同じ図に二つの縦軸で重ねると、二つの尺度の合わせ方が任意になり、データにない相関を読ませてしまう。

**縦に並べて x 軸（距離）を共有し、カーソルを同期させる。**
同じ地点で何が起きたかは、これで読める。
この判断は M3 で下したもので、[M3 の結果](m3-report.md)の 3 節に実装の詳細がある。

### 6.5 コース横断は行をコースにする

**この節は後から足した。** M10 の後に入れた「コース横断の評価」
（[#62](https://github.com/promodeler314-a11y/raceemu/issues/62)、[ロードマップ](roadmap.md)の 3.3 節）
の置き場と表の向きを決めた理由である。

距離とバ場を選ぶと、当たる全コースを同じ個体で走らせて並べる。
issue は「比較の面の列をコースにすれば表は作れる」と見立てていたが、**そのままでは作れない**。

- **列にすると幅が足りない。** 比較の面は列が設定で行が項目である。当たるコースは
  距離帯で選ぶと最大 26 本あり、これを列にすると幅 390 の画面に到底収まらない
  （`pnpm e2e` が横あふれを見ている）。行をコースにすれば、列は指標の 6 つで固定になる。
- **行の作りが噛み合わない。** 比較の行は「基準にないスキル」「基準から外したスキル」など、
  設定どうしの差を出すためのものである。コース横断は個体が 1 つで、動くのはコースだけなので、
  これらの行は全部同じ値になる。

そこで**向きを変えた別の表**にし、置き場は比較の面のままにした。
「並べて比べる」という問いは同じところにあるべきで、面を増やすとヘッダのタブが 7 つになる。

表の中では**同じ距離の行を区切ってまとめる**。
タイムは距離が違えば比べても意味が無いのに、1 列に並ぶと比べられてしまう。
区切りの中で最速のコースに印を付け、他の行はそこからの差で出す。
差には 95 % 区間を添える。コースどうしは別々に走らせているので、
試行を対応付けて引き算する探索の面の区間より広い（比較の面と同じ事情である）。

**順位条件は単騎の実行と同じ設定に従う。**
ここだけ別の回し方にすると、結果の面の数字とコース横断の表の数字が別の意味を持つ。
どちらで走らせたかは表の上と下に文で出す。判定した場合、束はコースごとに作り直す
（相手の走りがコースに依る）。そのぶんコース 1 本あたり数秒が余計にかかるので、
押す前に本数と見込み時間を出している。

距離の選び方は「ぴったりの値」と「距離帯」の両方を 1 つの選択欄に並べる。
チャンピオンズミーティングは距離帯が先に分かってコースが後から決まるので帯で引き、
育成中に「この個体はどのコースなら走れるか」を見る人はぴったりの距離で引く。
使い手が違うので、どちらかに寄せられない。

### 6.6 スキル一覧は事前に計算した表を読むだけの面にする

**この節は後から足した。** [#83](https://github.com/promodeler314-a11y/raceemu/issues/83)
「全スキル × 全コースの単体評価を事前計算して配る」の、画面側の決めごとである。
配る JSON の形は `packages/solver/src/skill-list.ts` が持ち、読む側は
`apps/web/src/skillList.ts` と `apps/web/src/components/SkillList.tsx` である。

#### 面を増やした

ヘッダのタブに **スキル表** を足した。6.5 節では「面を増やすとタブが 7 つになる」ことを
理由にコース横断を比較の面へ入れたが、この面は事情が違う。

- **いまの設定に依らない。** コース横断も探索も、左の設定と実行バーの下流にある。
  スキル一覧は事前に計算した表を読むだけで、1 レースも走らせない。
  設定を変えても表は動かないので、設定の下流に置くと嘘になる。
- **探索の面はすでに 3 つの塊を縦に積んでいる**（逆算・組み合わせ探索・近似の感度）。
  4 つ目として全スキルの表を積むと、探索の結果を見るまでに数千行ぶんスクロールする。

#### 軸はコースである。距離帯の選択欄はもう無い

**当初は距離帯で絞る作りだった。** 生成側が距離帯ごとに代表コースを 1 本だけ
測っていたので、画面の絞り込みも距離帯・バ場になっていた。
いまは**全コースを 1 本ずつ測る**ようになったので、画面も**コースを選ぶ**形にした。

同じ距離帯でも、コースが違えば直線の長さも坂もコーナーも違い、効くスキルが変わる。
距離帯で畳んだ表からは「中距離で強いスキル」しか読めない。
読みたいのは「このレースで強いスキル」である。

そこで画面の作りはこうなった。

- **コースはフィルタではなく、「どの 1 枚を取るか」である。** 一覧（`index.json`）に
  載っているコースを選択欄に出し、選ばれた 1 枚だけを取りに行く。
  137 コースを 1 枚にすると 25 MB を超えるので、まとめて取ることはしない。
- **選択欄はレース場でまとめる**（`optgroup`）。137 本を平らに並べても目当ての
  コースは見つからない。場でまとめると、ゲームの画面と同じ探し方になる。
- **既定は東京 芝2400m。** リポジトリの既定コースであり（`pnpm sim` も `pnpm cross` も
  ここを既定にしている）、他の実測と並べられる。置いていなければ一覧の先頭にする。
- **取った 1 枚は覚えておく。** コースを行き来しても 1 度ずつしか取らない。

残る絞り込みは**脚質**と**基準の個体**の 2 つだけである。
コースを選んだ時点で距離帯もバ場も決まっているので、それらの選択欄は要らない。

#### 測っていないコースは、無いのではなく測っていない

**全 137 コースが揃っているとは限らない。** 1 回では回りきらない（40 時間を超える）ので、
測れたところまでが一覧に載る。これは普通の状態である。

画面は「測ってあるのは N コースである」と数を出す。
出さないと、目当てのコースが選択欄に無いことを「壊れている」と読まれる。
行が無いことに 2 通りある（下）のと同じ話が、コースの側にもある。

#### 絞り込みは JSON が持っている軸だけにする

issue は「距離帯、脚質、コース群、バ場、季節、天候」で絞ると書いているが、
今回の版の `SkillListSettings` は**季節・天候・バ場状態を振っていない**（固定で 1 通り）。
無い軸の選択欄を出すと、選べるのに何も変わらないものになる。
そこで選択欄は **脚質・基準の個体** の 2 つに絞り（距離帯とバ場はコースが決める）、
振っていない軸は「1 通りしか持っていない」と文で書く。
軸が増えたら選択欄も増やす。増えたかどうかは JSON を見れば分かる（`file.settings`）。

「コース群（右回り、坂あり）」は入れていない。JSON のコースは
`location` / `course` / `distance` / `surface` / `category` しか持たず、
回りと坂は持っていないためである。足すなら生成側の話になる。

#### 基準の個体は `normal` / `strong` の 2 つだけにした

**ここは実データで一度壊した。** 記録として残す。

format 1 の生成側は `baselines` を 2 件ではなく 16 件持っていた（2 段 × バ場 2 × 距離帯 4）。
`id` は `normal:1:MIDDLE` のような複合で、`label` は「普通」「強い」の 2 語しか無い。
長距離の基準個体は短距離のそれよりスタミナが多い、という妥当な作りである。

画面は当初 `SkillListFilter.baseline` を**具体的な個体の id 1 つ**にしていた。
既定は `baselines[0]`、つまり `normal:1:SHORT` である。
すると**芝短距離の行しか当たらない**。全距離帯を選んでいるのに一部しか出ず、
距離帯を中距離にすると 0 件、バ場をダートにしても 0 件になった。
実データで 4 通りの絞り込みのうち 3 通りが全滅していた。

**原因は契約が id の作りを決めていなかったことである。**
`packages/solver/src/skill-list.ts` の例示は `normal` / `strong` のままで、
生成側が複合の id を使うことを画面側は知らなかった。

コース単位にしたことで、この問題はそもそも消える。
1 枚が 1 コースなら、スタミナはその 1 枚の `baselines` に入っていればよく、
id に面や距離帯を混ぜる必要が無い。そこで**契約が `id` を `normal` / `strong` の
2 つに固定した**（`SkillListTier`）。画面はその id でそのまま絞る。
知らない id を渡されたら先頭の個体に落とす（両段を混ぜない）。

選択欄にはスタミナを併記する。**コースごとの実測値**なので、
どの個体の話かがここで分かるようにしておく。

**手書きの見本だけのテストでは捕まらなかった。** 見本は書いた人が思っている形になるので、
生成側が実際に出した形とズレていても緑のままになる。そこで**配ってある実データそのものを
読む検査**を `apps/web/test/skill-list.test.ts` に置いてある。
一覧が指すファイルが全部あること、置いてあるファイルが全部一覧に載っていること、
どのコース・段・脚質で絞っても 0 件にならないこと、
**同じ距離帯の別のコースが同じ表にならないこと**（コース単位にした理由そのもの）を見る。
`pnpm e2e` も実データをそのまま読み、コースを切り替えて表が変わることを見ている。

#### 単位は秒を正にし、バ身は併記にとどめる

1 バ身 = 2.5 m はゲームからの裏取り前である（[#52](https://github.com/promodeler314-a11y/raceemu/issues/52)）。
そのうえ画面での換算は**裏取り前の値を 2 つ重ねる**。
JSON は秒しか持たないので、「1 秒が何メートルか」を別に置く必要があり、
そこには**そのコースの基準速度**（`setting.ts` の `baseSpeed`、2000 m で 20.0 m/s）を使っている。
コースが 1 本に決まっているので、換算に使う距離も 1 つに決まる。
実際の終盤は基準速度より速いので、この目安は実際よりやや小さめに出る。
だから表の並べ替えも比較も秒で行い、バ身は薄い色の 1 列に留めて、
裏取り前である旨を表の下に書く。

#### 「単体」であって「限界」ではない

何も持っていない構成へ 1 つだけ足したときの差である。
食い合うスキル（最終直線の加速どうし）は過大に出る。
探索の面の「単体」「限界」の 2 列と同じ区別なので、表の冒頭にそう書き、
既に何か持っている状態での効きは探索の面に送る。

#### 行が無いことには 2 通りある

`screen.ts` が走らせる前に落とした組（**確かに発動しない**）と、
この版がそもそも測っていない組である。
JSON は落とした数（`screenedOut`）をそのコースの 1 つの数としてしか持たないので、
画面もそこまでしか言えない。数を出し、2 通りあることを明記する。
どのスキルがどちらなのかまで言いたければ、生成側が組ごとに持つ必要がある。

**コースそのものが一覧に無い**のは 3 つ目の「まだ測っていない」で、上に書いたとおり
測ってあるコース数を出して言い分けている。

#### 内訳はコースごとではなく脚質ごとになった

表がコース単位になったので、1 行を押したときに降りる内訳も脚質ごとである。
絞り込みで脚質を 1 つに決めているときも、比べられるように 4 脚質すべてを出す。
発動位置の分布は JSON が持っていないので、ここには出せない（結果の面が実際に走らせて出す）。

#### 発動位置の分布は入れない

issue は「行を押すと、コースごとの内訳と発動位置の分布に降りる」と書いているが、
**内訳までしか作れない。** コースごとの内訳は同じ JSON の中でコースを跨いで集めれば
作れるが、発動位置は JSON が持っていない。
入れるなら生成側に列を足す話（別 issue）になるので、画面には出せないことを書いてある。
いまの設定での発動位置は、結果の面と詳細の面が実際に走らせて出す。

#### 取れなかったときに壊れない

表は数 MB あるので**バンドルに混ぜず、動的に取りに行く**
（`pnpm e2e` がバンドルの上限を見ている。本体は 21 kB しか増えていない）。
配布物には**静的ファイルだけを置いた版**があり、そこに表を載せていないことがある。
`searchApi.ts` と同じく、状態番号ではなく**中身が JSON かどうか**で判断し、
取れなければ日本語で言って終わる。他の面はこの表に依っていないので、そのまま使える。
`pnpm e2e` が、404 が返る場合と HTML が返る場合の両方を突いている。

置き場は issue のとおり `apps/web/public/skill-list/<版>.json` で、版はデータと計算式と
相手の分布の指紋から決まる。**読む側はその名前を当てられない**ので、
`skill-list/index.json` に名前を教える 1 枚を置き、読む側はまずそれを見る。
`index.json` がそのまま表であっても読めるようにしてあるのは、
生成側が 1 枚しか置かない作りを選んだときに壊れないようにするためである。

#### 版を画面に出す

表の値は**相手の分布に依る**（`defaultFieldProfile`）。
相手の作り方が変われば数字が変わるので、版（`file.version`）と 4 つの指紋
（スキル・コース・計算式・相手の分布）を表の上に出す。
どの版を見ているかが分からないまま数字だけが出回ることを避けるためである。

## 7. 正しさの確認

本家と乱数列が違う以上、1 レースの厳密一致は取れない。
そこで二段構えにする。

- **決定論に近い設定での一致確認**：スキル発動率とランダム区間を固定し、確率的な発生イベントの係数を 0 にした設定を用意する。この条件では乱数の影響がごく小さくなるため、本家をローカルの JVM で実行した結果とタイムを直接比較できる。差が残る箇所は、残存する乱数源を特定して切り分ける。
- **統計量での一致確認**：代表的な数十通りの設定について、両者を 1 万回ずつ走らせ、平均タイムと最大スパート率を比較する。差が標準誤差の範囲に収まることを確認する。

確認に使った設定と期待値は、ゴールデンテストとしてリポジトリに置く。
係数を触ったときに、意図しない挙動変化を検出できるようにする。

加えて、部分式ごとの単体テストを置く。
最大体力、毎秒消費、目標速度、加速度、ラストスパートの候補選択は、入力と出力を手計算できるため、テストの費用対効果が高い。

## 8. データの扱い

- **コースデータ**：本家はソースに JSON を埋め込んでいる。本アプリでは `packages/data` に JSON として置き、ビルド時にバンドルする。
- **スキルデータ**：本家は起動時に GitHub から取得している。本アプリではビルド時に取り込んだものを既定とし、任意で最新版を取得して差し替えられるようにする。取得に失敗してもアプリが動くことを優先する。
- **更新手順**：本家のデータ更新に追従するため、取得と検証を行うスクリプトを用意し、スキーマが変わったときにテストが落ちるようにする。

設定の永続化には **IndexedDB** を使い、直近の設定と保存済みスナップショットを保持する。
スナップショットは全試行の集計を抱えるため、`localStorage` の容量にすぐ当たる。
互換性のため、保存形式にはバージョン番号を持たせ、読めない版は捨てて既定値で立ち上げる。

## 9. 実装の段取り

各段階の終わりに動くものが残る形で区切る。

1. **M1 計算モデルの移植**：`packages/sim` を書き、Node 上で 1 レースを計算できるようにする。決定論に近い設定で本家と突き合わせ、一致を確認する。ここで 1 試行あたりの所要時間を実測する。
2. **M2 並列実行と集計**：Worker プールと統計集計を実装する。UI はまだ最小限のフォームでよい。1 万試行の所要時間を測り、5 節の目標と照合する。
3. **M3 UI の骨格**：設定パネル、サマリ、フレームグラフを実装する。ここで単独のツールとして使える状態になる。
4. **M4 比較と共有**：スナップショット比較、URL 共有、モバイル対応、分布表示を実装する。
5. **M5 逆算**：目標を先に決めて必要なステータスを求める機能。任意試行の再生もここに含める。
6. **M6 フィールド軌跡モデル**：順位条件を判定できるようにする。
7. **M7 組み合わせ探索**：スキル貢献度モードと、予算内で最良のスキル構成を探す機能。

M5 と M7 の詳細は[逆算と組み合わせ探索の設計](solver-design.md)に、M6 の詳細は[順位条件の扱い](order-condition.md)にある。
実測の結果は[M1](m1-report.md)から[M7](m7-report.md)までの各報告にある。

M1 と M2 の順序は動かせない。
計算が本家と合っていることと、速度の見通しが立っていることが、以降の作業の前提になるためである。

## 10. 未決の論点

- **データ更新の追従方法**：本家のスキルデータ形式が変わったときに、手作業をどこまで減らせるかは未検討である。スキルデータの取得と差し替えも、いまはビルド時に取り込むだけで、実行時に最新版へ入れ替える経路は無い。
- **近似の表示**：6.3 節で決めた印をまだ実装していない。無視された順位条件は M6 でフィールド軌跡モデルに置き換わったが、距離差と内外の位置は[M6 の結果](m6-report.md)の 5 節のとおり未実装のままであり、その条件を持つスキルには印が要る。
- **画面の骨格**：[モックと実装のズレ](ui-gap.md)に挙げた差分のうち、詳細のイベント一覧、比較の作り直し、図の段数、逆算と探索の置き場が未決または未着手である。
- **探索機能の計算予算**：[M3 の結果](m3-report.md)の 2 節で 4 コアの環境の実測が出た（東京 芝2400m の 1 万試行で 5.90 秒）。この上で M5 の完走逆算が数十秒かかることが[M5 の結果](m5-report.md)の 6 節で分かっている。刻みを利用者に選ばせるかを含め、残る点は[逆算と組み合わせ探索の設計](solver-design.md)の 8 節にまとめてある。

# スキル画面の読み取り

ゲームの画面を写した画像から、所持しているスキルを取り込む。
名前を一つずつ手で選ぶ手間を省くための機能である。

## 1. どこで動かすか

読み取りはサーバ側で行う。
ブラウザから `/api/ocr/skills` に画像を送り、当たったスキルの一覧を受け取る。

サーバ側にしたのは、学習データが 35 MB あるためである。
ブラウザ側で動かすとこれを配ることになり、[配信](deploy.md)している本体 1.4 MB に対して重すぎる。

代償として、**静的ファイルだけを置いた版ではこの機能が使えない**。
`/api` が無いためである（GitHub Pages に配っていた版は廃止した。[配信](deploy.md)の 5 節）。

口が無いことは、状態番号ではなく**応答の中身が JSON かどうか**で判断する。
静的配信だけの環境が POST に返す状態番号は決まっていない。
405 を返すもの（GitHub Pages がそうだった）もあれば、開発用のサーバのように 200 で index.html を返すものもある。
番号で見分けようとすると取りこぼし、HTML を JSON として読もうとして `Unexpected token '<'` で落ちる。
実際にそれを出してしまったので、`pnpm e2e` の静的サーバも POST に HTML を返す形にして、同じことが起きたら落ちるようにした。

## 2. どの学習データを使うか

tesseract の日本語の学習データには三通りある。
同じ見本の画像（スキル名が 10 個並んだもの）で比べた。

| 種類 | 大きさ | 時間 | 結果 |
| --- | ---: | ---: | --- |
| `tessdata_fast` | 2.4 MB | 194 ms | `一匹狼` を `ー忠狼` と読み違えた |
| `tessdata`（標準） | 35.7 MB | 197 ms | 10 件すべて正しい |
| `tessdata_best` | 13.7 MB | — | 動かない |

**標準のものを使う。**
`tessdata_fast` は軽いが、短い名前を読み違える。
短い名前は 1 文字違うだけで別のスキルと同じくらい近くなるので、後段で拾い直すのが難しい。

`tessdata_best` は浮動小数の LSTM を使い、SIMD を有効にした版の tesseract を要求する。
tesseract.js が読み込む既定の中身では `DotProductSSE` が見つからずに落ちる。

大きさは 15 倍になるが、速度は変わらない。
サーバ側に置くならイメージが 35 MB 増えるだけで済む。
35 MB をリポジトリに置くわけにはいかないので、イメージを組むときに取ってくる（`scripts/fetch-tessdata.mjs`）。

## 3. 読み取った文字をスキルに戻す

読み取った文字はそのままではスキル名と一致しない。
実際に見た崩れ方は二通りある。

**書き分けの揺れ**：丸印が `○` にも `〇` にもなる。
標準のモデルは 1 文字ずつ空白を空けて返す。
これは正規化で消える。

**文字の取り違え**：`一匹狼` が `ー忠狼` になる。
これは正規化では消えないので、編集距離が近いものを拾う。

### 3.1 正規化

互換文字を潰し（NFKC）、空白を落とし、見た目の同じ文字を一つに寄せる。

寄せるのは丸印（`○` `〇` `◯` `O` `0`）と、長音と横棒と漢数字の一（`ー` `一` `－` `-`）である。
後者を同一視してよいかは、全 2106 件の名前で確かめた。
**この二つを同じ文字として扱っても、区別が付かなくなる組は一つも無い。**

### 3.2 引き当て

正規化した名前と読み取った行のあいだで編集距離を取り、`1 - 距離 / 長い方の文字数` を一致の度合いとする。
0.6 を下回るものは捨てる。

**短い名前には厳しい下限（0.75）を置く。**
3 文字の名前は 1 文字違うだけで 0.67 まで落ちる一方、別の 3 文字の名前とも同じくらい近くなるためである。
`ー忠狼` は正規化しても `一匹狼` と 1 文字違い（0.67）で残るが、この下限で落ちる。
読み違えたものを黙って別のスキルとして取り込むより、拾わないほうが害が小さい。

一致には 2 番目の候補との差も添える。
差が小さいものは画面で「要確認」として印を付け、読み取った文字を並べて出す。
ただし**正規化して完全に一致したものは、似た名前が隣にあっても紛らわしくない**。
`中距離コーナー○` は `中距離コーナー◎` と 1 文字しか違わないが、読み取った文字が前者と完全に一致しているなら迷う余地は無い。

## 4. 口の形

```
POST /api/ocr/skills
content-type: image/png
（本文は画像そのもの。上限 8 MB）

200 {"text": "...", "matches": [{"id","name","rarity","sp","text","score","margin","runnerUp"}], "elapsedMs": 0}
501 学習データの置き場が指定されていない
415 content-type が画像でない
413 画像が大きすぎる
```

tesseract は Worker として 1 本だけ立て、依頼を並べて順に流す。
立ち上げに数百ミリ秒かかるので使い回し、読み取り自体は直列にする。
中では 1 スレッドしか使わないため、並べても速くならない。

### 失敗が必ず終わるようにする

tesseract.js の失敗の伝わり方には落とし穴が二つある。

**`errorHandler` を渡さないと、プロセスごと落ちる。**
仕事が失敗したとき、worker からの受け口でそのまま `throw` する。
worker_threads の受け口から出た例外は uncaughtException になり、Node が終了する。
読み取りが失敗しただけでレースの計算まで巻き添えになり、外からは proxy の HTML エラー画面として見える。

**渡すと今度は、promise が解決も拒否もしないまま残る。**
学習データが見つからない場合がこれで、待っている側は永久に返らない。
`createWorker` の中で `workerResReject` に届く経路と、`errorHandler` にだけ届く経路があるためである。

そこで `errorHandler` が受け取った失敗を自前の合図に変えて競争させ、時間切れも重ねる。
**読み取りは必ず終わる。**
結果が返るか、理由の付いた失敗になるかのどちらかである。

失敗したら worker を畳んで作り直す。
中途半端な状態のまま次の依頼を流すと、二度目以降が何を返すか分からなくなる。

## 5. 本物の画面で確かめた結果

[M10](m10-report.md)の時点では、検査に使っていたのはスキル名を縦に並べて組み立てた画像だけだった。
その後、実際の「ウマ娘詳細」画面（ステータス、適性、キャラの写真、スキル一覧を含む全体）で試す機会があり、精度が大きく落ちることを確認した。

### 5.1 何が起きたか

キャラ詳細画面をまるごと送ると、**スキルらしい文字が見つからなかった**という結果になった。
同じ難易度の画像（背景の模様、丸いアイコン、装飾つきの枠、縦に長いスキル一覧）を組み立てて再現したところ、抽出した文字はこう乱れていた。

```
⑧ ワ ク ワ ク ク ラ イ マ ッ ク ス     ← 読み取れている
( mo ロ ラ ェ ッ ッ ー               ← 「弧線のプロフェッサー」が壊滅
0 ペ ル ー                          ← 「十万バリキ」が壊滅
```

**スキルの丸いアイコンと、金枠・装飾つきの背景が、隣接する文字を巻き込んで壊す。**
[3.2 節](#32-引き当て)の下限（0.6、短い名前は 0.75）はこの壊れ方まで拾うようには作っていないので、正しく落ちている。
低い下限に緩めて拾わせることも試したが、今度は無関係な文字列まで誤って一致してしまい、実害のほうが大きい。

この再現では、読み取り自体は落ちなかった（2.2 秒で完了）。
4 回連続で読み取らせてもクラッシュせず、メモリも 88 MB から 370 MB で頭打ちになった。
**精度が落ちるのであって、落ちるわけではない。**

### 5.2 二値化で直った

**tesseract 自身の自動二値化が、この壊れ方の原因だった。**
tesseract は渡された画像を自前で二値化してから読む。
グレースケール化しただけの画像を試したところ、無加工より悪化して 21 件中 0 件になった。
人の目にはグレースケール画像も正しく読める形をしているので、tesseract 側の判断が破綻しているとしか考えられない。

そこで、**グレースケール化と固定の閾値での二値化まで済ませてから渡す**ことにした（`apps/api/src/preprocess.ts`）。
tesseract に二値化の判断をさせないようにする、という向きの変更である。
実機同等の見本での結果は次のとおりである。

| 前処理 | 一致数 |
| --- | ---: |
| 無加工 | 14 / 21 |
| グレースケールのみ | 0 / 21 |
| グレー + 閾値 170 で二値化 | 21 / 21 |

閾値は 165 から 175 の範囲がよく、170 と 175 では[M10](m10-report.md)の簡単な見本（10 件）が[3.2 節](#32-引き当て)の一致の度合いで満点（1.0、[正規化](#31-正規化)した文字列が完全に一致した状態）となり、すべて引き当てられた。
180 を超えると難しい見本のほうが急に崩れる（8/21）。
**明るさを引き伸ばす前処理（sharp の `normalize`）は試したところ、無いほうが良い結果になったので入れていない。**
これを挟むと、同じ閾値の数字が指す実際の二値化の境界が変わってしまい、簡単な見本の一部（「好転一息」）で一致の度合いが 0.75 まで落ちた。

意図的に暗くした画像では固定閾値がまったく効かなくなった（0/21）。
ただしこの検査は 8 bit に丸めた画像をさらに暗くする作為的なもので、本物の暗い写真とは条件が違う。
うまくいかない場合に備えて、閾値は `RACEEMU_OCR_THRESHOLD` で調整できるようにしてある。

### 5.3 それでも残る当面の回避策

閾値を 170 に合わせたことで、合成した見本の上では簡単な画面と実機同等の画面のどちらも確信度 1.0 で全問正解している。
それでも、**スキル一覧の部分だけを切り抜いて送るほうがなお確実である。**
この 170 という数字は合成した見本だけで決めたものであり、本物の写真の明るさや圧縮のかかり方は確かめていない（5.4 節）。
ステータスやキャラの写真を含めない、スキル名が並んでいる帯だけの画像であれば、送る量も減り、閾値の調整に依存しなくて済む。

画面の案内にはこの二つ（切り抜きを勧める文言と、精度についての注記へのリンク）を添えてある。

### 5.4 まだ確かめていないこと

- **本物の写真で閾値が合っているか。** 5.2 節の数字はすべて合成した見本によるものであり、実機の写真そのものでは確かめていない。
- **サーバ側で領域を切り出せるか。** 「ウマ娘詳細」画面はレイアウトがほぼ決まっているので、上部のステータス欄を機械的に除いてからスキル一覧の帯だけを読み取れる見込みがある。決め打ちできれば、ユーザーに手で切り抜かせる手間を省ける。
- **一覧が縦に長い場合、画面を分けて送る必要があるか。** 今回の見本は 1 画面に収まる長さだった。実際のスキル一覧はこれより長くなることが多い。
- **スキル名以外の文字を拾っていないか。** ステータスの数値（「⑫②0」のような丸数字化した誤読）は 3.2 節の下限で落ちているが、これは狙って落としたわけではなく、たまたま短い日本語のスキル名とは形が違ったために落ちている。もっと紛らわしい誤読が来たときにどうなるかは確かめていない。
- **固定閾値ではなく、局所的に適応する二値化が要るか。** 画面の中で明るさが場所ごとに大きく違う場合、単一の閾値では対応できない可能性がある。

**この節の内容は 6 節の分類器に置き換わった後も残してある。** 分類器が「その形の画面ではない」と判断したときは、ここに書いた文字認識にそのまま落ちるためである。

## 6. 文字認識ではなく分類で読む

5 節の課題（丸いアイコンと装飾つきの背景が隣接する文字を巻き込んで壊す）は、二値化した合成見本では直ったが、実際に本物の写真を送ってみると崩れ方は変わらなかった。文字を 1 つずつ読もうとする限り、この壊れ方は原理的に付きまとう。

### 6.1 umacapture という先行例

[umasagashi/umacapture](https://github.com/umasagashi/umacapture)（MIT）は、同じ「ウマ娘詳細」画面からスキルや因子を読み取る Windows/Android/iOS 向けの既存ソフトである。ソースを読むと、**文字認識を一切使っていない**ことが分かった。

行ごとの矩形を切り出し、学習済みの分類器（ONNX、`native/src/chara_detail/chara_detail_recognizer.h`）にそのまま画像として渡して、約 1800 種のスキルのどれかを直接当てている。文字を分解しないので、アイコンや装飾つき背景は「そのスキルの見た目の一部」として扱われ、壊れない。

umacapture 自身も、この方式には数ピクセルの誤差が致命的になる副作用があると認めている（`native/src/cv/detail_crop_calibrator.h` のコメント）。画面内の目印（ヘッダーの境界線など）を検出して基準位置を割り出す専用の較正機構を持つのはそのためである。

### 6.2 借りたものと自分で作ったもの

| | 由来 |
| --- | --- |
| `apps/api/assets/skill-classifier/model.onnx` | umacapture が配布する学習済みモデルそのもの。`license.md` により**パブリックドメイン**（クレジット表記も不要） |
| `apps/api/assets/skill-classifier/label-map.json` | こちらで生成した「モデルの分類番号→うちのスキル ID」の対応表 |
| 行の切り出し（較正） | umacapture の較正機構を読んで方針だけ借り、実装は自前で組んだ |

umacapture 側の `labels.json`（モデルの分類番号→スキル名の対応表）は Cygames の著作物を含むため、リポジトリにはコピーしていない。`scripts/build-skill-classifier-labels.ts` が、手元に置いた `labels.json` と `packages/data` の既存スキル一覧を名前で突き合わせ、対応表だけを吐き出す。1832 件中 1775 件（96.9%）が一致した。残り 57 件は「先行駆け引き」「かく乱」のような、対戦相手にしか掛からない debuff で、うちのデータベースには元々無い。

### 6.3 行の切り出し方（`apps/api/src/skill-classifier.ts`）

umacapture は画面内の目印を検出して基準位置を割り出す較正機構を持つが、そこで使っている目印（閉じるボタンの下端など）はデスクトップ版の窓の飾りを前提にしており、スマートフォンでのスクリーンショットにはそのまま使えない。実機の写真 1 枚で、うちの入力に合う目印を探し直した。

1. **タブの下端をヘッダーから見分ける。** ブランドの緑色は上部ヘッダーとアクティブなタブの両方に使われるが、ヘッダーは全幅に近く、タブは画面の一部（3 分の 1）しか占めない。ヘッダーより下で「部分幅の緑」を探すと、スキル一覧の直前にあるタブの下端が見つかる。見つからなければ、スキル一覧だけを切り抜いた画像が来たとみなして画面の先頭から探す。
2. **左列のアイコンの位置で行を数える。** スキル名の左にある丸いアイコンは彩度が高い（色は問わない）。左列が来る横幅（0〜11%）の中でこの条件に合う横方向の塊を縦に探すと、行の数とそれぞれの上下端が分かる。右列のアイコンは検出に使わない。一覧は詰めて並ぶので、行数が奇数のときに空くのは最後の行の右側だけであり、左列だけを見れば数え間違えない。
3. **文字だけを切り出す。** アイコンの実際の右端はそのまま使わず、横幅に対する割合（実機の1枚で目視して合わせた固定値）で文字の帯を切り出す。アイコンの右端をそのまま使うと、モデルが学習した切り出し方（アイコンの縁の柔らかい部分を少し含む）とずれて、確信度の高い誤答が増えることが分かった。
4. **確信度で微調整する。** 手順 1〜3 の検出・固定値には数ピクセルの誤差が残る。切り出しの左端を ±10px・行の中心を ±6px・高さを 24〜36px の範囲で振り、いちばん確信度が高い切り出しを採用する。**正しい位置ならほぼ 1.0、ずれていれば 0.6 以下に落ちる**という差がはっきりしているため、これで実用上の精度が出る。

金色・虹色の縁取りが隣の行まで続いていると、アイコンの絵柄内部の隙間（走る人の影絵の白地）をまたぐ処理が複数行を 1 つに繋げてしまうことがある。1 行ぶんの高さは絵柄次第で 44〜75px ほど揺れるため、高さそのものでは複数行かどうか見分けが付かない。行の間隔（前後の行の上端どうしの差）の中央値のほうが安定するので、それより明らかに高い塊だけを複数行とみなして等分している。

**アイコンの色を問わない（2.）のは、あとから直したものである。** 当初は「ブランドの緑を除く」判定にしていたが、これは適性系スキルなど緑色のアイコンの行まで巻き込んで見落としていた。タブの検出（1.）はその下端より下しか見ないので、ブランドの緑と紛れる心配は無い。

**確信度の微調整（4.）も、当初は横 5 通り×高さ 4 通り×縦 7 通り＝ 140 通りを総当たりしていた。** 一覧が長い（複数画面をつなげた）写真では推論が数千回に膨れ、Cloudflare など手前のゲートウェイのタイムアウトに掛かって 502 になった。3 方向はほぼ独立に決まるため、縦→高さ→横の順に、それまでの最良位置を土台に 1 つずつ決めるよう直した（7+4+5 = 16 通り）。あわせて、切り出し自体も `sharp` のパイプラインを毎回作るのをやめ、最初に読んだ生の画素配列から直接切り出して縮小するようにした。

### 6.4 実機の1枚での結果

実際に読み取りに失敗していた本物の「ウマ娘詳細」画面（5.1 節の壊れ方を引き起こしたのと同じ写真）で試したところ、**23 件のスキル欄すべてを確信度 0.99 以上で正しく当てた**。一覧の最後で片方の列だけ空く行（右側に何も無い）は、確信度 0.137 に落ちて正しく除外された。

複数画面をつなげた、行数がずっと多い（32 行分）別の実機の写真を試した利用者から、正しく読めない・長く待った末に JSON 以外が返ることがあると報告があった。この写真そのものはファイルとして受け取れておらず値は確かめていないが、症状（緑色のアイコンを持つスキルの見落とし、行数が多いと時間がかかりすぎる）から上記の2つの不具合（緑色を除く判定と、確信度の微調整の総当たり）を特定して直した。この写真での再検証はまだできていない。

`CLASSIFIER_MIN_CONFIDENCE`（`apps/api/src/http.ts`、既定 0.5）を下回る分類は捨てる。正しい行の確信度（0.99 以上）と空の行の確信度（0.5 以下）の間には大きな差があるため、この閾値は動かす必要が今のところ無い。

`/api/ocr/skills` はこの分類器をまず試し、行を 1 つも見つけられなければ（その形の画面ではない、または画像として読めない）5 節までの文字認識に落ちる。`RACEEMU_TESSDATA` を指定していない環境でも分類器だけは動く。

### 6.5 まだ確かめていないこと

- **実機の写真で検証できているのは 1 枚だけである。** 6.3 節の固定値（アイコンを探す横幅の割合、文字の帯の位置）はこの 1 枚に合わせたものであり、他の解像度・機種・OS のスクリーンショットでどこまで通用するかは確かめていない。行数が多い別の写真での不具合報告を受けて緑色アイコンの見落としと処理時間の問題は直したが、その写真自体で直ったことまでは確かめられていない。
- **スキル一覧以外のタブ（継承・育成情報）や、因子の画面。** umacapture は両方に対応するモデルを配っているが、こちらはスキル一覧しか組み込んでいない。
- **一覧が縦に長く、1 画面に収まらない場合。** umacapture は動画キャプチャからスクロールを追跡して 1 枚に再構成する仕組みを持つが、こちらは静止画 1 枚しか受け取らない前提のままである。利用者が手元で複数のスクリーンショットを縦につなげて送るぶんには、行の検出は（アイコンさえ見つかれば）そのまま機能するはずだが、つなぎ目のずれなどは確かめていない。
- **umacapture 側のモデルが更新・撤去された場合の追従。** `model.onnx` は今の版を固定でリポジトリに置いてあるので、当面は影響しない。スキルが新しく追加されたときの対応表の更新は `scripts/build-skill-classifier-labels.ts` を参照。
- **合成した見本（`hard-skill-list.png` など）では、正しく「その形ではない」と判断できないことがある。** 実機と色味・配置が違う合成見本の一部で、分類器が誤って行を検出することを確認している。これらの見本を分類器の検査に使うのは避け、5 節までの文字認識の検査にとどめてある。

## 7. ステータスと適性を読む

スキル一覧に続けて、同じ「ウマ娘詳細」画面の**上半分**（ステータスの数字 5 つと適性 10 個）を読めるようにした。

### 7.1 スキル一覧より易しい

スキル一覧は行数も位置も可変なので、画面内の目印から行を探す必要があった（6.3 節）。上半分は違う。**並びが固定**なので、内容領域さえ決まれば、あとは割合で切り取るだけで済む。文字の周りに巻き込むものも無い。数字と適性の記号は無地の板の上に 1 つずつ離れて置かれており、5 節で文字認識を壊していた「丸いアイコンと装飾つきの背景」が隣に来ない。

したがってここは分類器ではなく、既にある tesseract で足りる。

### 7.2 座標は umacapture の設定から取った

割合の値は umacapture（MIT）の `assets/config/chara_detail/recognizer.json` の `status_header` から写した。ゲーム画面の並びという事実であって、学習データでもモデルでもない。

| | 値（内容領域の横幅を 1 とする） |
| --- | --- |
| ステータス 5 つ | 横 0.1074〜0.9518 を 5 等分、縦 0.4833〜0.5111 |
| 適性 10 個 | 3 段（0.5648 / 0.6204 / 0.6759）に 2・4・4 |

**縦も横幅で割る。** ここが要である。umacapture の `FrameAnchor`（`native/src/cv/frame.h`）は長さの単位 `unit_size` を `intersection.width()` に取り、縦横どちらの位置もこれで割っている。画面の縦横比は機種ごとに違うが、内容の配置は横幅に対して決まるので、縦を高さで割ると機種ごとにずれる。

内容領域（`intersection`）は、umacapture では取り込んだ窓の中のゲーム描画領域である。こちらが受け取るのはスマートフォンのスクリーンショットで、ふつうは画面全体がゲームなので、**上下左右の黒帯だけを落として**残りを内容領域とする。

明るい帯も落とすようにしていたことがあったが、この画面は背景が淡いクリーム色で、**画面全部が「明るく一様な行」に当たって内容を削り落とした**。額縁が付くのは画面比の合わない端末に入る黒帯であって、白い余白ではない。黒だけを見る。

### 7.3 丸囲み数字

`jpn` の学習データは丸囲み数字（①②…）を字として持っており、ゲームの数字をそちらに読む。**しかも二桁を 1 文字にまとめる。** 見本では `1247` が `⑫④⑦` になった。

ここで「読む文字を `0123456789` に絞る」と、候補から丸囲みが外れて**何も返らなくなる**。絞りは逆効果である。絞らずに読ませ、丸囲みを展開して（⑫ → `12`）数字だけを拾うと元の並びに戻る。5 つとも正しく読めた。

適性のほうは逆に、絞りが効く。出てくるのは S から G までの 8 文字だけなので、`B` と `8`、`S` と `5` の取り違えが起きなくなる。10 個すべて正しく読めた。

同じ見本を `eng` の学習データで読ませると、丸囲みにならず `1247` とそのまま読んだ。実機の写真で数字が揺れるようなら、数字だけ `eng` に読ませるのが次の手である。`eng.traineddata` は 22 MB あり、イメージに積む分が増えるので、必要が分かってから入れる。

### 7.4 位置だけでは別の画面を見分けられない

縦さえ足りていれば、切り出しの矩形は画像の中に収まってしまう。実際、スキル一覧だけを切り抜いた画像（620×780）でも 15 か所すべてが収まり、**もっともらしい数字を 1 つ返した**。位置の検査だけでは、別の画面を渡されたことに気付けない。

5 つの枠のうち数字として読めた数で見分ける。本物なら 5 つとも読める。にじみで 1 つ 2 つ落ちることは許し、3 つ未満なら別の画面とみなして 422 で断る（`/api/ocr/status`）。スキル一覧の画像は 1 個しか読めず、正しく断られる。

### 7.5 適性は 10 個のうち 3 つだけ使う

画面には適性が 10 個あるが、この計算モデルが持つのは距離・バ場・脚質の 3 つである。どれを当てるかは、いま選んでいるコース（バ場と距離区分）と脚質で決まる。

画面には読み取った 10 個を全部出し、当てる 3 つに印を付ける。**コースや脚質を変えたら取り込み直す必要がある**ことが、印を見れば分かる。

### 7.6 適性は文字ではなく色で読む

記号は立体的に飾られた字で、**文字認識には向かない**。二値化すると輪郭だけが残って中が抜ける。閾値を上げて中を埋めると、今度は潰れた塊になる。実機の 1 枚で閾値を 170 から 210 まで振り、切り出しの余白と段組みの指定も変えて総当たりしたが、いちばん良い組み合わせ（余白 0.004、1 語として読む、3 倍に拡大）でも **10 個のうち 7 個**で、しかも `B` を `E` と読む取り違えが混ざった。

**色のほうがはるかにはっきりしている。** 実機 3 枚（横 608 と 810 の 2 通り）の 30 か所を測ったところ、同じ階級は色相が 1 度も違わなかった。

| 階級 | 色相 | 彩度の高い画素 | 測った数 |
| --- | ---: | ---: | ---: |
| S | 42 | 33〜34% | 4 |
| A | 24 | 33〜35% | 10 |
| B | 342 | 18% | 1 |
| C | 106 | 26% | 1 |
| D | 203 | 27% | 3 |
| E | 286 | 23% | 2 |
| F | 245 | 1.4〜6.0% | 3 |
| G | 無し | 0.0% | 6 |

いちばん近い組は `A` と `S` の 18 度で、それ以外は 40 度以上離れている。許容を 8 度に取れば、どの 2 つも取り違えない。

色相は円周上の量なので、平均は sin と cos を平均してから角度に戻す。`342` のような 0 をまたぐ値を素直に平均すると、真ん中あたりの別の色になる。

**`F` と `G` の境目に注意が要る。** `F` は淡い青紫で、彩度の高い画素が 1.4% しか無いことがある。灰色とみなす境目を 2% にしていたときは、その `F` を `G` と答えていた。`G` は 6 か所すべてで 0.0%（1 画素も無い）なので、0.5% で分かれる。

色が確かめ済みのどれにも近くなければ、文字認識の答えに任せる。8 階級すべての色が分かったので、いまのところこの受け皿に落ちるのは、色の付いていない何かが写った場合だけである。

### 7.7 実機 3 枚で確かめた

| 写真 | 大きさ | 結果 |
| --- | --- | --- |
| 1 | 608×2340 | ステータス 5・適性 10 すべて一致 |
| 2 | 810×2789 | 同上 |
| 3 | 810×2454 | 同上 |

**45 か所すべてを正しく読んだ。** 横幅が 608 と 810 の 2 通りあり、縦横比も 3 枚とも違う。切り出しを横幅に対する割合で決めている（7.2 節）ので、そのまま通る。

**目印の検出も較正も要らなかった。** umacapture は数ピクセルの誤差を潰すための較正機構を持つが（6.1 節）、それはスキル一覧の行のように分類器へ渡す場合の話である。上半分は並びが固定で、数字も記号も無地の板の上にあるため、割合だけで足りた。

途中で 3 つ直した。

- **ステータスの上限が低すぎた。** 2000 を超える読み取りを切り出しのずれとみなして捨てていたので、スピードの 2165 を落としていた。因子と覚醒で 2000 は普通に超える。画面の入力欄と同じ 2500 に合わせた。
- **適性を文字として読んでいた。** 7.6 節のとおり色に替えた。
- **`F` を `G` と答えていた。** 7.6 節のとおり、灰色とみなす境目を下げた。

写真はゲームの著作物なのでリポジトリには置かない（umacapture 側の `labels.json` を置かないのと同じ理由）。持っている人だけが、写真を置いた場所を指して走らせる。無い番号は飛ぶので、1 枚だけ持っている人も走らせられる。

```
RACEEMU_REAL_SCREENSHOT_DIR=~/shots pnpm test
```

期待値は `apps/api/test/status-reader.test.ts` にある。

### 7.8 まだ確かめていないこと

- **確かめたのは 3 枚である。** 横幅は 2 通りしかなく、機種も OS も同じかもしれない。とくに内容領域の求め方（黒帯だけを落とす）は、上下に別の色の帯が入る端末で外れうる。3 枚のうち 2 枚は画面上部に通知バーが写っているが、黒ではないので落とさず、それで正しく通っている。
- **`B` と `C` は 1 か所ずつしか測っていない。** 他の階級は 2 か所以上ある。色相がぴたりと揃う性質からして揺れるとは考えにくいが、測った数は少ない。
- **評価点は読んでいない。** 位置は分かっている（`EVALUATION_RECT`）が、この計算モデルは使わない。
- **umacapture の分類モデルは使っていない。** 同じ `modules.zip` に `status_value/prediction.onnx` と `aptitude/prediction.onnx` が入っており、スキルと同じくパブリックドメインである。この環境からは配布元（`data.umacapture.com`）に届かない（proxy が 403）。実機 3 枚で 45 か所すべて当たっている以上、置き換える理由は無い。**他の機種で崩れたときの次の一手**として控えている。

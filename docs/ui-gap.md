# モックと実装のズレ

[UI 骨格のモック](../design/README.md)と、[M3](m3-report.md) から [M7](m7-report.md) で作った `apps/web` の実装を突き合わせた記録である。

**モックを正とする。**
モックは設計書だけを見て起こしたもので、実装と突き合わせずに描いた。
そのため差分には、実装を寄せるべきものと、モックの側が実装を知らずに描いてしまったものの両方が混じる。
本書では差分を並べ、どちらを動かすかを項目ごとに書く。

対応の欄は次の三つを使う。

- **実装を寄せる**：モックが正しく、コードを直す。
- **モックを直す**：実装の判断のほうが妥当で、モックの側を後で調整する。
- **未決**：どちらが良いか決めきれていない。

## 1. 画面の骨格

| 項目 | モック | 実装 | 対応 |
| --- | --- | --- | --- |
| ヘッダの区切り | 設定／結果／比較／詳細 の 4 区分 | 見出しと説明文のみ | 実装を寄せる |
| 左右の配分 | 設定 468px 固定、結果側が残り全部 | `lg:grid-cols-2` で等分 | 実装を寄せる |
| 設定の折り畳み | 結果を見るときは 280px の要約レールに畳む | 畳めない | 実装を寄せる |
| フッタ | 状態表示と、モデルの出所および AGPL v3 とソースへのリンク | なし | 実装を寄せる |
| 逆算・探索の置き場 | モックに描いていない | 設定列の下に常設 | モックを直す |

**フッタは体裁の問題ではない。**
[改良版の設計](webapp-design.md)の 2 節は「利用者がソースを取得できる状態にしておく必要がある」「リポジトリへのリンクを画面上に置く前提で設計する」と書いている。
`apps/web` の画面には現在そのリンクがない。
AGPL v3 の下で配信する前に埋める必要がある。

逆算と探索は、M5 と M7 で足した機能であり、モックを描いた時点では画面に存在しなかった。
これはモックの側の漏れである。

## 2. 結果の見せ方

| 項目 | モック | 実装 | 対応 |
| --- | --- | --- | --- |
| 先頭の数字 | 平均タイムを 44px の主数字にし、残りをタイルで並べる | 11 行のラベルと値の表 | 実装を寄せる |
| 標準誤差 | 平均タイムに併記 | なし | 実装を寄せる |
| 所要時間の見積もり | 実行前に「約 n 秒の見込み」を出す | 実行後の実測のみ | 実装を寄せる |
| 分布の分位点 | p5・p50・p95 を図に重ねる | なし | 実装を寄せる |
| 分布からの掘り下げ | 帯をクリックしてその 1 本を開く | 最速・中央・最遅の 3 ボタン | 未決 |
| 空状態 | 説明とプリセット 3 つ、本家設定の読み込み口 | 「まだ実行していない。」の一文 | 実装を寄せる |

「分布からの掘り下げ」を未決にしたのは、3 ボタンのほうが操作が確実で、外れ値を選ぶという目的も概ね果たしているためである。
帯のクリックはヒット領域が細く、モバイルでは扱いにくい。
両方を置くのが答えかもしれない。

### 2.1 「基準との差」という語が二つの意味で使われている

これは名前の衝突であり、直さないと確実に誤読を招く。

- モックでは、**保存した基準スナップショットとの差**を指す。
- 実装（`Summary.tsx`）では、`finishTimeMax / 1.18` すなわち**コースの基準タイムとの差**を指す。

同じラベルで別のものを出している。
モックの意味を採り、コース基準タイムのほうは別の名前にする。

## 3. 比較

| 項目 | モック | 実装 | 対応 |
| --- | --- | --- | --- |
| 分布の重ね合わせ | 3 件の分布を 1 つの図に重ね、直接ラベルを付ける | なし | 実装を寄せる |
| 行のまとめ方 | ステータス／コース／スキル／結果 の 4 群 | 平坦な 12 行 | 実装を寄せる |
| 同じ値の畳み込み | 「差のある項目だけ表示」で畳み、件数だけ出す | 差のある値を太字にする | 実装を寄せる |
| 基準列の選択 | どの列を基準にするか選べる | 左端が固定で基準 | 実装を寄せる |
| スキルの差 | どのスキルが増減したかを行に出す | スキル数だけ | 実装を寄せる |
| 信頼区間 | 差に 95% 区間を併記 | 点推定のみ | 実装を寄せる |
| 列数の上限 | 3 列まで | 制限なし | 未決 |

列数の上限をモックで 3 にしたのは、重ね合わせる分布の色を 3 系列までに抑えるためである。
表だけなら 4 列以上でも読める。
図と表で上限を変えるか、表も 3 列に揃えるかは決めていない。

## 4. 詳細

| 項目 | モック | 実装 | 対応 |
| --- | --- | --- | --- |
| 開いている試行の明示 | 試行番号とシードを出す | 試行番号のみ（見出し内） | 実装を寄せる |
| 分布内の位置 | 小さい図で位置を示す | なし | 実装を寄せる |
| 前後の試行へ移動 | ボタン 2 つ | なし | 実装を寄せる |
| その試行の結果 | タイム・出遅れ・掛かり・スパート成否などを一覧 | なし | 実装を寄せる |
| イベント一覧 | 時刻・位置・種別・内容の表 | なし | 実装を寄せる |
| 共通乱数の入口 | 「この試行の乱数で別の設定を走らせる」 | なし | 未決 |
| 図の段数 | 速度／スキル発動レーン／体力 の 3 段 | 速度／残り体力／勾配 の 3 段 | 未決 |

イベント一覧は差分のなかで最も大きい。
フレーム列は `detail.frames` に持っているので、スキル発動とフェーズ境界とコーナー進入を拾えば作れる。

図の段数を未決にしたのは、モックが「スキル発動レーン」を独立段に置いたのに対し、実装は「勾配」を独立段に置いたためである。
どちらも情報としては要る。
4 段に増やすか、スキル発動を速度段の上に重ねるかを決める必要がある。

## 5. 図の色の割り当てが食い違っている

同じパレット（dataviz の既定）を使っているが、役割の割り当てが違う。

| 系列 | モック | 実装 |
| --- | --- | --- |
| 速度 | `#2a78d6`（青） | `#2a78d6`（青） |
| 目標速度 | 灰色の破線（文脈色） | `#eb6834`（橙） |
| 体力 | `#eb6834`（橙） | `#1baf7a`（アクア） |

**モックの割り当てを採る。**
理由は二つある。

目標速度は速度と同じ量の参照線であって別の系列ではないので、カテゴリ色を 1 枠使うのは割に合わない。
そして `#1baf7a` は明色面でのコントラストが 3:1 を下回るため、直接ラベルの併記が要る色である。
体力のような主要な系列に充てるより、比較の 3 列目のように使用頻度の低い枠に回すほうが無理がない。

実装のコメントは「明色面での aqua は 3:1 を下回るため、体力の図は単系列にして見出しで名前を出す」と書いており、この制約は認識したうえで色を充てている。
判断としては筋が通っているが、モックの割り当てのほうが制約に当たらない。

## 6. 見た目の土台

| 項目 | モック | 実装 |
| --- | --- | --- |
| 書体 | IBM Plex Sans JP ／ IBM Plex Mono | Tailwind の既定（システムフォント） |
| 角丸 | 3px | `rounded-lg`（8px） |
| 区切り | 罫線と余白 | カード（枠線と背景） |
| 配色 | ライト固定 | ライトとダークの両対応 |

ダーク対応は実装が自分で足したもので、モックには無い。
**これはモックを直す。**
夜に長時間見るツールなので、ダークを捨てる理由がない。

書体・角丸・区切りはモックを正とし、実装を寄せる。
ただしこれらは見た目そのものなので、出先で判断しにくい。
他の項目を片付けたあとに回す。

## 7. 直す順序

1. **フッタとソースへのリンク**（1 節）。ライセンス上の要求であり、他と独立している。
2. **「基準との差」の名前の衝突**（2.1 節）。誤読を生むので早く消す。
3. **空状態とプリセット**（2 節）。初めて開いたときに何をすればよいかが分からない状態を先に解く。
4. **イベント一覧**（4 節）。差分のなかで情報量が最も増える。
5. **比較の作り直し**（3 節）。行の群分け、基準列の選択、分布の重ね合わせ。
6. **色の割り当て**（5 節）。
7. **画面の骨格**（1 節）と**見た目の土台**（6 節）。実物を見ながら詰める必要があるので最後に回す。

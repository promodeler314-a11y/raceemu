## 2. 乱数ストリームの分離

[逆算と組み合わせ探索の設計](solver-design.md)の 1.1 節で決めたとおり、乱数源を用途ごとに分けた。

```ts
const rng = new RngSet(seed, trial);
rng.stream('startDelay')            // 出遅れ
rng.stream('temptation')            // 掛かり
rng.stream('sectionSpeed', '7')     // 区間 7 の目標速度乱数
rng.stream('skillLot', skill.id)    // このスキルの発動抽選
```

種は `(seed, trial, ストリーム名)` のハッシュから導く。
スキルを 1 つ足しても他のストリームの出目は変わらないので、共通乱数によるペア比較が成立する。

副産物として、任意の試行を後から再現できるようになった。
`simulate(setting, { seed, trial })` は何度呼んでも同じ結果を返す。

## 3. 本家との一致

### 3.1 確かめ方

本家を JVM でビルドして参照値を出力させ、それと突き合わせた。
手順は `packages/sim/test/golden/README.md` にある。

乱数の実装が違うので 1 レースの厳密一致は取れない。
そこで、レース前に確定する導出値は厳密に、タイムは分布として比べた。

### 3.2 結果

導出値は 39 項目すべてが小数第 9 位まで一致した。
比べたのは基準速度、補正後ステータス、最大体力、v0 から v3、最高スパート速度、加速度 a0 から a3、位置取り争いや追い比べや脚色十分の各係数、賢さスキル強化倍率などである。

タイムの分布は、3 つのケースで平均の差が標準誤差の範囲に収まった。

| ケース | 本家の平均 | 移植版の平均 | 本家の標準偏差 |
| --- | ---: | ---: | ---: |
| 東京 芝2400m 先行 スキル無し | 118.228 秒 | 118.225 秒 | 0.179 |
| 札幌 芝1200m 逃げ スキル無し | 56.474 秒 | 56.628 秒 | 0.075 |
| 東京 芝2400m 先行 スキル 6 種 | 117.814 秒 | ほぼ一致 | 0.202 |

3 番目のケースには、パッシブ、回復、目標速度上昇、ランダム発動区間、近似条件を持つスキルを入れてある。
スキルエンジン全体がまとめて検証されたことになる。

### 3.3 条件の網羅

全 2106 件のスキル定義について条件をコンパイルし、未対応の型が出ないことを確かめた。
残った未対応は `succession_skill_count` の 1 種類（スキル「連綿」の 1 箇所）だけで、これは本家も未対応のまま条件を落としている。
新しい型が増えればテストが落ちるので、実装漏れに気付ける。

## 4. 速度

1 試行あたりの所要時間を実測した。単一スレッド、Node 22、tsx 経由である。

| コース | 距離 | 1 試行あたり |
| --- | ---: | ---: |
| 札幌 芝1200m | 1200 m | 0.99 ms |
| 阪神 芝1800m(外) | 1800 m | 1.55 ms |
| 東京 芝2400m | 2400 m | 2.10 ms |

距離にほぼ比例する。フレーム数が距離に比例するので当然である。

[改良版の設計](webapp-design.md)の 5 節では「2000 m 級のコースで 1 万試行を数秒」を目標にしていた。
単一スレッドでは 2400 m の 1 万試行に約 21 秒かかるので、目標には届かない。
8 並列で約 3 秒になる見込みであり、目標の達成は M2 の並列化に懸かる。
この見積もりは M2 で実測して確かめる。

なお、この数字はフレーム列を記録しない場合のものである。
記録する場合は 1 レースあたり千数百個のオブジェクトを作るため、これより遅くなる。

## 5. 移植で判明したこと

本家のコードを 1 行ずつ追う過程で、二つ気付いた点がある。どちらも挙動を合わせるためそのまま移植した。

**初期レーンの補正**：本家の `Track.initialLaneAdjuster` は `location == 10101` を条件にしている。
`location` はレース場の ID（10001 から 10017）で、10101 はコースの ID なので、この条件は成立しない。
コースの ID と取り違えている可能性があるが、挙動を変えないためそのまま移植し、コメントを残した。

**ポジションキープの区間指定**：脚質ごとのペースダウン区間は長さ 10 の真偽値リストで、区間番号でそのまま添字を引いている。
区間番号は 1 始まりなので、先行は区間 1、差しは区間 1 と 4、追込は区間 1、3、8 でペースダウンする。
[解析メモ](race-emulator-analysis.md)には区間 2 などと書いていたが、これは添字の読み違いだったので修正した。

## 7. データを本家に追随させる

1 節の抽出は手作業の一度きりで、以来 `assets/skills.json` と `assets/courses.json`
は更新されていなかった。新しいウマ娘やスキルは本家のデータが更新され次第
そちらに載るので、取り直さない限りいつまでも古いままになる。

`packages/data/scripts/sync-game-data.py` が本家から取り直し、差分を報告する。

```
python3 packages/data/scripts/sync-game-data.py
```

週次の [`sync-game-data`](../.github/workflows/sync-game-data.yml) がこれを呼び、
差分があれば `chore/sync-game-data` に積んで下書き PR を出す（ブランチは毎回
main から作り直すので積み上がらない）。新しい条件・効果の型（`type` 文字列）
が増えていれば、その PR の CI で「スキル条件の網羅」の検査が落ちるので、
コード側の対応が要ることに気付ける。

**ただし GITHUB_TOKEN が作った PR は、GitHub の仕様で pull_request のワークフロー
（`pages.yml` の typecheck/test/build）を自動では起こさない。** `SYNC_PAT` という
名前で個人アクセストークンを repository secret に登録すると、ワークフローは
GITHUB_TOKEN の代わりにそちらを使い、CI も普段どおり自動で走るようになる
（未設定なら今までどおり GITHUB_TOKEN に落ち、CI は手動で走らせる必要がある。
PR 本文がどちらの状態かを都度書く）。

登録手順（管理者権限を持つ側の手作業。トークンの発行はこちらからはできない）：

1. https://github.com/settings/personal-access-tokens/new を開く（発行するのは
   `promodeler314-a11y` アカウント自身）。
2. Resource owner を `promodeler314-a11y`、Repository access を
   「Only select repositories」→ `raceemu` のみに絞る。
3. Repository permissions で **Contents: Read and write**、
   **Pull requests: Read and write** を選ぶ（Metadata は自動で付く）。他は不要。
4. 有効期限を決めて（無期限は避ける）発行し、表示されたトークンをコピーする
   （この画面を閉じると二度と見えない）。
5. https://github.com/promodeler314-a11y/raceemu/settings/secrets/actions を開き、
   「New repository secret」→ Name に `SYNC_PAT`、Value に発行したトークンを
   貼って追加する。

有効期限が切れたら 1〜5 を繰り返して値を更新する。トークンそのものは
このリポジトリのどこにも残らない（secrets はワークフローの実行時にしか展開されず、
ログにも値は出ない）。

あわせて、抽出時に単一行へ詰めていた 2 ファイルを、この節を書くときに
2 スペース区切りの整形済み JSON へ直した。中身は変えていない
（`pnpm test` が全件通ることを確認済み）。差分を 1 行の丸ごと書き換えとしてしか
出せなかった状態では、この自動化を作っても PR の差分が読めなかった。

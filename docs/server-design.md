# サーバ側で探索を回す設計

自前の k3s クラスタで組み合わせ探索を走らせ、結果を画面で受ける。
Cloudflare Tunnel 越しに外部公開し、狭いコミュニティで使う前提である。

## 1. なぜサーバに出すのか

いまの探索の候補は「利用者が選んでいるスキル」に固定されている（`apps/web/src/store.ts` の `candidates`）。
数百あるスキル全体から予算内の最良を選ぶ、という本来の問いには答えていない。
これは設計の判断ではなく、ブラウザで回すという制約から来ている。

候補 20 個のいまと、全スキルを候補にした場合の規模を並べる。

| | 候補 20 個 | 候補 200 個 |
| --- | ---: | ---: |
| 単体評価 | 4,000 レース | 40,000 レース |
| 局所探索 1 巡 | 約 35,000 レース | 約 160,000 レース |

スマホの数コアで回す量ではない。
**サーバに出して初めて、いまは答えられていない問いに答えられる。**

[逆算と組み合わせ探索の設計](solver-design.md)の 3.6 節に挙げた予算曲線と採用頻度も、探索を何本も走らせる必要があるため同じ理由で入っていない。

## 2. 譲らないこと：サーバが無くても動く

アプリはいまクライアント側だけで完結している。
**API は加速装置であって、依存先にはしない。**

理由が三つある。

- 静的配信だけの版が生き続ける。クラスタを持たない人にも渡せる。
- クラスタが落ちている間も使える。
- 配布物が自己完結していれば、AGPL の下で渡すものが「アプリ一式」で済む。

実装としては、API の宛先が設定されていなければ今までどおりブラウザの Worker で回す。
設定されていれば、そちらに投げる選択肢が画面に出る。

## 3. 形

### 3.1 ジョブにする

1 本の探索が 25 万レース規模になる。
分単位でかかるので、HTTP の要求と応答を往復させる形では持たない。

- `POST /api/search` が受け付けてジョブ ID を返す。
- `GET /api/search/{id}` が進捗と、終わっていれば結果を返す。
- `DELETE /api/search/{id}` で中断する。

`optimizeSkills` は既に `onProgress(message)` と `AbortSignal` を受け取るので、この三つはそのまま対応する。

### 3.2 出入りの型はもう在る

**新しく定義する型がほとんど無い。**

要求は `OptimizeContext` と `OptimizeOptions` のうち値だけのもので、`base` は `SerializableRaceSetting`、つまり Worker に送るために既にプレーンな値へ落としてある形である。

応答は `OptimizeResult` がそのまま JSON になる。
型付き配列（`Float64Array` と `Uint8Array`）は `Evaluation` の内側だけにあり、`OptimizeResult` からは外に出ていない。

つまりサーバ側は `WorkerPool` を `nodeWorkerFactory` で作り、既存の `optimizeSkills` をそのまま呼ぶ薄い包みになる。
**計算モデルにも探索にも手を入れない。**

### 3.3 走らせ方

**単一の Deployment に面内のキューを持たせる。**
1 探索につき Kubernetes の Job を 1 個立てる形は採らない。
イメージ取得と起動の待ちが毎回乗るだけで、この規模では得が無い。

ポッドの中で `nodeWorkerFactory` の `WorkerPool` を 1 つ持ち、キューから 1 本ずつ流す。

## 4. 実際に転ぶところ

### 4.1 コンテナの CPU 上限が Node から見えない

`nodeWorkerFactory` の並列数は `os.availableParallelism() - 1` である。
これが見ているのは CPU アフィニティ（`sched_getaffinity`）であって、Kubernetes の `resources.limits.cpu` が設定する CFS のクォータではない。

**16 コアのノードに `limits.cpu: 2` で置いたポッドは、16 と答える可能性が高い。**
Worker が 15 本立ち、2 コアぶんの枠を奪い合って全体が遅くなる。

並列数は環境変数で渡す。
`WorkerPool` のコンストラクタは既に第 2 引数で並列数を受け取れるので、追加の作りは要らない。

入れる前に、ポッドの中で実際に何が返るかを測る。
`apps/web/e2e/smoke.mjs` がブラウザの場所を決め打ちしていて CI で落ちたのと同じ種類の誤りである。

### 4.2 tsx が実行時に要る

`packages/sim/src/parallel/node-worker-bootstrap.mjs` は `tsx/esm/api` を登録してから TypeScript の本体を読み込んでいる。
Node の型剥がしがパラメータプロパティを扱えないためである。

いま `tsx` は devDependency なので、そのままの構成でイメージを作ると Worker が起動しない。
実行時の依存に移すか、サーバ向けにはあらかじめコンパイルする。

### 4.3 上限が無いと 1 人で埋まる

1 本 25 万レースを、数コアのクラスタで回す。
外部公開する以上、次の三つは入れる。

- 同時に走らせるジョブの数（まずは 1）
- 待ち行列の長さの上限。超えたら受け付けを断る
- 1 ジョブあたりのレース数の上限。候補数と予算と試行回数から見積もって弾く

## 5. 公開の仕方

Cloudflare Tunnel が既に通っているので、TLS と経路はそちらに任せる。

**認証は Cloudflare Access を前に置く。**
アプリにもサーバにも認証の実装を持たない。
狭いコミュニティに配るのであれば、これで足りる。

**アプリと API を同一オリジンで配る。**
別オリジンにすると CORS の設定が要り、平文で出そうとすると mixed content で落ちる。
同じホスト名の下に静的ファイルと `/api` を並べれば、どちらも起きない。

## 6. AGPL

**ここで初めて 13 条が実際に効く。**
自分だけで動かしている間は関係なかったが、他人にネットワーク越しに使わせるなら、その人がソースを取得できる必要がある。

フッタのリンクは既にある（`apps/web/src/App.tsx`）。
ただし**動かしている版と push してある版がズレると、リンクがあっても意味がない。**
自前ホストは手で入れ替えられるぶんズレやすい。

そこでビルド時にコミットの SHA を埋め、フッタに出す。
見ている人が、いま動いているものに対応するソースを特定できる状態にする。

## 7. 段取り

1. ポッドの中で `availableParallelism()` が何を返すかを測る。4.1 の前提の確認であり、ここが違うと並列数の設計が変わる。
2. `apps/api` を作る。`optimizeSkills` を呼ぶだけのジョブ API と、面内のキュー。
3. イメージと マニフェスト。`tsx` の扱い（4.2）をここで決める。
4. アプリ側に宛先の設定と、投げ先を選ぶ口を足す。宛先が無ければ今までどおり。
5. コミットの SHA をフッタに出す。
6. 全スキルを候補にできるようにする。**ここまで来て初めて 1 節の目的が果たされる。**

1 から 3 まではサーバを立てる作業で、4 から 6 が使えるようにする作業である。
途中で止めてもアプリは壊れない。2 節の前提がそれを保証する。

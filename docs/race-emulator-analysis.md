# ウマ娘レースエミュレータ（mee1080/umasim）の解析

対象は https://mee1080.github.io/umasim/race/ で公開されている「ウマ娘レースエミュレータ移植版」である。

このページはブラウザ上で動くクライアント完結のアプリケーションであり、実体は GitHub リポジトリ [mee1080/umasim](https://github.com/mee1080/umasim) の `race` モジュールと `compose` モジュールを WebAssembly にビルドしたものである。
本稿の記述は、公開ページの配信元である同リポジトリのソースコード（`race/src/commonMain` および `compose/src/commonMain`）を読んだ結果に基づく。
稼働中のページそのものには本稿の作成環境からアクセスできなかったため、画面の見た目ではなく計算ロジックの記述に絞る。

レース計算のコアは [urakagi/uma-clock-emu](https://github.com/urakagi/uma-clock-emu) からの移植であり、各ソースファイルの冒頭にその旨が明記されている。
ライセンスは AGPL v3 である。

## 1. 何を計算するツールか

このエミュレータは、**1 頭だけのウマ娘を秒間 15 フレームで数値積分し、ゴールまでのタイムを求める運動シミュレータ**である。
他の出走馬を実体として持たない点が最大の特徴であり、順位や進路妨害といった対人要素は、後述する確率的な近似に置き換えられている。

1 回のシミュレーションは乱数に強く依存するため、アプリは同じ設定で既定 100 回（回数は入力可能）走らせ、平均タイムや最大スパート率といった統計量を出力する。
つまり、単発の結果を見るツールではなく、**モンテカルロ法で設定の良し悪しを比較するツール**である。

### 入力

- ウマ娘のステータス（スピード、スタミナ、パワー、根性、賢さ）、やる気、脚質、距離適性、バ場適性、脚質適性、人気、枠番
- コース（レース場、距離とバ場、バ場状態、出走人数）
- 所持スキル（固有スキルのレベルを含む）と、相手から受けるデバフスキルの個数
- ポジションキープの扱い、スキル発動率の固定、ランダム発動区間の引きの良さ、試行回数

### 出力

- 平均タイム、最速タイム、最遅タイム、完走率、最大スパート率
- スパート時の余剰体力、ゴール時の残り体力
- 位置取り調整の回数、持久力温存の発生率と距離、追い比べの完走率と時間
- スキルごとの発動率、平均発動位置、2 回発動率、フェーズ接続率、速度上昇が無効になった割合
- 1 回目の試行についての速度と体力のグラフ、および全フレームの詳細
- スキル貢献度モード（あるスキルを外した場合の遅れ、または候補スキルを 1 つ取った場合の短縮）

## 2. 実行環境とデータの供給

UI は Compose Multiplatform で書かれ、Kotlin/Wasm にビルドされて `docs/race/` から配信される。
計算はすべてブラウザ内で走り、サーバは静的ファイルを返すだけである。
Web 版の並列度は 1 に固定されている（`compose/src/wasmJsMain/.../platform.wasmJs.kt` の `defaultThreadCount`）ため、試行回数を増やすとその分だけ実時間がかかる。

データの供給元は二つに分かれる。

- **コースデータ**：`race/.../data/rawData.kt` に JSON 文字列として埋め込まれている。各コースについて距離、バ場、回り、コーナー、直線、坂、レーン最大幅、助走距離、基準タイムを持つ。
- **スキルデータ**：起動時に `https://raw.githubusercontent.com/mee1080/umasim/refs/heads/main/data/skill_data.txt` を取得する。2000 件を超えるスキルが、発動条件と効果の配列として記述されている。

スキルがデータ駆動である結果、新スキルの追加はデータ更新だけで済み、条件の種類（`type` 文字列）が新規なときだけコード側の対応が要る。

## 3. シミュレーションの骨格

エントリポイントは `RaceCalculator.simulate` であり、初期化とフレームループの二段構成になっている。

```kotlin
fun simulate(setting: RaceSetting): Pair<RaceSimulationResult, RaceState> {
    val state = setting.initializeState()
    val result = state.progressRace()   // position < courseLength の間 updateFrame()
    return result to state
}
```

時間の刻みは `framePerSecond = 15`、すなわち 1 フレーム 1/15 秒である。
ループはゴール到達か 5000 フレーム（約 333 秒）で打ち切られる。

位置は二つの尺度で区切られる。

- **フェーズ**：序盤が 0 から 1/6、中盤が 1/6 から 2/3、終盤が 2/3 から 5/6、ラストが 5/6 以降。速度と加速度の脚質補正、減速度、スキル条件がこれに従う。
- **区間**：コースを 24 等分したもの。掛かりの発生区間、目標速度の区間乱数、ポジションキープや位置取り調整の有効範囲がこれで指定される。

初期化では、枠番から初期レーン（`horseLane = 11.25 / 18` m 刻み）と枠順を決め、パッシブスキルを適用してステータスを確定させ、出遅れ時間を `U(0, 0.1)` 秒で引き、掛かり発生の抽選と区間乱数の生成を行う。
助走距離のあるコースでは位置を `-runUp` から始め、0 m を通過した瞬間の時刻を記録して、助走を含むタイムと含まないタイムの両方を出せるようにしている。

各フレームの処理順は次のとおりである。

1. 下り坂モードの開始と終了の判定（1 秒ごと）
2. 掛かりの終了判定と、区間到達による掛かりの開始
3. ポジションキープの状態遷移
4. デバフの発動
5. 位置取り争い、追い比べ、位置取り調整、持久力温存、リード確保、スタミナ勝負、全開スパートの判定
6. 目標速度と加速度を求めて `move()` で位置と体力を更新
7. 終盤に入った瞬間であればラストスパート計算と脚色十分の適用
8. スキル発動条件の近似状態の更新（1 秒ごと）とスキル発動判定、効果切れの回収
9. レーン移動

## 4. 速度のモデル

### 基準速度とステータス補正

コースごとの基準速度は距離だけで決まる。

```
baseSpeed = 20.0 - (courseLength - 2000) / 1000.0
```

ステータスは、やる気倍率（絶好調 1.04 から絶不調 0.96）とバ場補正、そしてパッシブスキルの加算を経て「補正後ステータス」になる。
1200 を超える分は半分に圧縮される（`calcExceedStatus`）。
スピードにはさらに、コースの得意ステータス指定に応じた 1.05 から 1.2 の倍率がかかる。
賢さには脚質適性倍率（S で 1.1、G で 0.1）がかかる。

### 目標速度

```
序盤と中盤: baseSpeed * 脚質係数[phase]
終盤以降  : baseSpeed * 脚質係数[phase]
            + sqrt(補正後スピード / 500) * 距離適性係数
            + (補正後根性 * 450)^0.597 * 0.0001
共通      : + baseSpeed * 区間乱数[現在区間]
```

区間乱数は 24 区間ぶんをレース開始時にまとめて引く。
上限は `(賢さ / 5500) * log10(賢さ / 10) * 0.01` で、そこから一様分布で最大 0.0065 引かれる。
賢さが高いほど上限が上がり、かつ下振れの影響が相対的に小さくなる。

この基本値に対し、ポジションキープの倍率、発動中スキルの速度加算、坂の補正（上り坂は `-|勾配| * 200 / 補正後パワー`、下り坂モード中は `+|勾配| / 10 + 0.3`）、位置取り争いや追い比べなどの速度加算が順に足し込まれる。

### 加速度と減速度

```
acceleration = c * sqrt(500 * 補正後パワー) * 脚質係数[phase] * バ場適性係数 * 距離適性係数
c = 上り坂なら 0.0004、それ以外は 0.0006
```

スタートダッシュ中は `+24.0` という桁違いの加速度が乗り、速度が `v0 = 0.85 * baseSpeed` に達した時点でダッシュが終わる。
減速度はフェーズごとに定数（序盤 -1.2、中盤 -0.8、終盤以降 -1.0）で、体力が尽きると -1.2、ペースダウン中は -0.5 になる。
速度の下限は、スタートダッシュ中を除き `0.85 * baseSpeed + 0.001 * sqrt(補正後根性 * 200)` である。

### 位置の更新とコーナーロス

```kotlin
val moveLength = simulation.totalSpeed * timeAfterDelay
val cornerLoss = currentCorner?.let {
    moveLength / it.length / 4 * 2 * PI * simulation.currentLane
} ?: 0.0
simulation.position += moveLength - cornerLoss
```

コーナーでは走行レーンが外側にあるほど進行距離が削られる。
レーンは `applyMoveLane` が管理し、序盤は内へ寄せ、最終コーナー以降は外へ持ち出し、速度スキル発動時には 40 パーセントの確率で 1 頭ぶん外へ動く。
この外への移動が、コーナーロスという形でタイムに跳ね返る。

## 5. 体力のモデル

最大体力は距離と補正後スタミナから決まる。

```
spMax = 距離 + 0.8 * 補正後スタミナ * 脚質係数
脚質係数: 逃げ 0.95、先行 0.89、差し 1.00、追込 0.995、大逃げ 0.86
```

毎秒の消費は速度の二次関数である。

```
consume = 20 * (現在速度 - baseSpeed + 12)^2 / 144 * バ場係数
終盤以降は * spurtSpCoef、spurtSpCoef = 1 + 200 / sqrt(600 * 補正後根性)
```

これに状態ごとの倍率がかかる。
下り坂モード中は 0.4 倍、掛かり中は 1.6 倍、ペースダウン中は 0.6 倍、逃げの位置取り争い中は 1.4 倍から、掛かりと重なる大逃げでは 7.7 倍まで跳ね上がる。

回復スキルは `spMax * 効果値 / 10000` を加算し、上限を超えた分は無駄（waste）として記録される。
回復のたびに、終盤以降であればラストスパートが再計算される。

## 6. ラストスパートの決定

中盤から終盤に切り替わったフレームで `calcSpurtParameter` が走る。

まず最高スパート速度で走り切る場合の必要体力を計算し、足りていればそのまま最大スパートとする（この判定が「最大スパート率」として集計される）。
足りない場合は、終盤基準速度 `v3` から最高速度までを 0.1 刻みで候補にし、それぞれ「その速度で走れる距離とその後を `v3` で走る」ときの所要時間を求めて昇順に並べる。
そして速い候補から順に、確率 `15 + 0.05 * 補正後賢さ` パーセントで採用する。

賢さが高いほど最適な候補が選ばれやすいという、ゲーム側の挙動を確率で表現した部分である。
必要体力にすら届かない場合は、スパートせず `v3` のまま押し切る。

## 7. スキルエンジン

### 発動抽選と条件

レース開始時に、所持スキルごとに `100 - 9000 / 賢さ`（下限 20）パーセントで発動権を抽選する。
権利を得たスキルは、条件式を評価するクロージャに変換されて保持される。

条件は `[[A, B], [C]]` のような二重配列で、内側が AND、外側が OR である。
`SkillChecker.kt` が各条件タイプを次の三種に振り分ける。

- **レース前に確定する条件**：脚質、バ場、距離種別、コース ID、人気、基礎ステータスなど。真偽値を 1 回だけ計算して固定する。
- **毎フレーム評価する条件**：残り体力割合、経過時間、区間、コーナー番号、坂、フェーズ、発動済みスキル数など。
- **ランダム区間条件**：「終盤ランダム」「コーナーランダム」のように、レース前に発動区間（幅 10 m）を抽選しておき、その区間に入ったかどうかで判定する。

ランダム区間の引きは UI から固定できる。
最速、1/4、中間、3/4、最遅を選ぶと、区間内の相対位置がその値に固定される。

### 効果の適用

発動したスキルは `OperatingSkill` として登録され、持続時間が過ぎると回収される。

- 持続時間には `距離 / 1000` の倍率がかかる。2400 m では表示値の 2.4 倍である。
- クールダウンは `cd * (距離 / 1000 * 15)` フレームで、既定値 500 は事実上の 1 回限りを意味する。
- レア、固有、進化スキルの目標速度上昇には、賢さと脚質とフェーズから決まる強化倍率（`getWisdomSkillBuff`）がかかる。
- 効果値のうち「所持スキル数に応じて」「残り体力に応じて」のような可変分は `SkillEffect.calcValue` で条件分岐し、確認しようのない条件（ファン数、チーム編成など）は最大値前提で固定されている。その旨はスキル説明の注記として UI に表示される。

## 8. 他の出走馬をどう近似しているか

単騎シミュレーションである以上、他馬に依存する挙動は作り物で補うしかない。
このエミュレータはその近似を隠さず、種類ごとに分けて実装している。

### ポジションキープ

序盤から中盤（区間 10 まで）の速度調整には、4 つのモードが用意されている。

- **近似**：脚質ごとに決め打ちした区間でペースダウンする。先行は区間 1、差しは区間 1 と 4、追込は区間 1、3、8 が該当する。
- **仮想ペースメーカー**：先頭役のウマ娘をもう 1 頭ぶん丸ごとシミュレートし、その位置との差でスピードアップ、追い越し、ペースアップ、ペースダウンを遷移させる。設定画面で先頭役のステータスとスキルを別途入力する。
- **一定確率でスピードアップ**：逃げ向けに、指定確率でスピードアップだけを発生させる。
- **無し**

速度への影響はスピードアップ 1.04 倍、追い越し 1.05 倍、ペースダウン 0.915 倍（中盤は 0.945 倍）などの倍率である。

### 位置と接触にまつわる条件の確率近似

「前が壁」「追い抜き」「周囲にウマ娘」のような条件は、`approximateConditions` に定義された確率過程で置き換えられている。
1 秒ごとに、開始確率と継続確率で状態を更新するマルコフ連鎖、あるいは値ごとの確率分布からの抽選である。

```kotlin
"blocked_front" to ApproximateStartContinue("前方ブロック(鋼の意志など)", 0.07, 0.50)
"overtake" to ApproximateMultiCondition(
    "追い抜きモード", listOf(
        ApproximateStartContinue("逃げ", 0.05, 0.50) to { 脚質が逃げ },
        ApproximateStartContinue("先行", 0.15, 0.55) to { 脚質が先行 },
        ApproximateStartContinue("その他", 0.20, 0.60) to null,
    )
)
```

確率は脚質やフェーズで切り替わる。
この値は UI の「発動条件近似設定」に一覧表示され、利用者が意味を確認できるようになっている。
追い抜きモードは条件判定だけでなくレーン移動にも影響するため、コーナーロスを通じてタイムにも効く。

### 無視される条件

順位、順位率、他馬との距離差、他馬のスキル所持、内外の位置取りといった条件は `ignoreConditions` に列挙され、判定から外される（多くは「満たしている前提」として扱われる）。
たとえば冒頭で引いたスキルデータの例のように、順位率条件を持つ固有スキルは、距離割合の条件だけで発動することになる。

`ignoreConditions` に載っていない型でも、`SkillChecker.kt` に分岐が無ければ同じく落ちる。
**`random_lot_shared` がそれにあたる。**
「勝負師」「やまっけ」「鉄火のギャンブラー」の 3 つが持つ、当たり外れを 1 回だけ引いて使い回す抽選である（`random_lot` は条件ごとに引き直す）。
落とすと条件を満たした扱いになるので、本家ではこの 3 つが必ず発動する。

どれも人気で二分された枝を持つ。
「勝負師」なら 4 番人気以下で 60%、3 番人気以内で 30% である。
枝は人気で排他なので、引く回数が 1 回か 2 回かは結果に出ない。

**移植版はこの抽選を実装している**（`packages/sim/src/skill/condition.ts`）。
必ず発動する扱いは、持っているだけでステータスが上がることを意味し、探索の結果を歪めるためである。
実測した発動率は、勝負師が 60.3% と 29.9%、やまっけが 30.0% と 14.7%、鉄火のギャンブラーが 59.7% と 29.9% で、いずれもデータの値に一致する。

### デバフ

相手から受けるけん制や眼光などは、種類ごとの個数を入力する形で受け取り、レース開始時に発動位置を抽選しておく。
発動時の効果は `spMax * 値 / 10000` の体力減少であり、速度低下としては扱われない。

## 9. 近年の追加挙動

ゲーム側の仕様追加に合わせて、終盤の細かい挙動が個別に実装されている。
いずれも根性やパワー、スタミナが一定値を超えたときに効く形になっている。

- **位置取り争い**：逃げが 200 m 地点から発動する。継続時間は `(700 * 根性)^0.5 * 0.012` 秒、速度加算は `(500 * 根性)^0.6 * 0.0001` で、体力消費が最大 7.7 倍に膨らむ。
- **追い比べ**：最終直線かつ体力 15 パーセント以上のとき、1 秒ごとに 40 パーセントで発動し、体力 5 パーセントで終了する。速度と加速度が根性に応じて上がる。
- **脚色十分**：終盤突入時にパワーが 1200 を超えていれば、数秒間の加速度ボーナスが付く。掛かりや位置取り争いを経験していると係数が下がる。
- **位置取り調整と持久力温存**：区間 11 から 15 で 2 秒ごとに判定する。終盤に必要な体力に対して余裕がなければ温存に入り、余裕があれば 80 パーセントで位置取り調整に入って体力を使う。
- **リード確保**：同じ区間で 30 パーセントの確率、追込は対象外。
- **スタミナ勝負**：2100 m 超のコースで最高スパート速度に達したとき、スタミナ 1200 超過分に応じて速度が上がる。
- **全開スパート**：スピード 2000 超で最高スパート速度に達したとき、通常の速度とは別枠の速度と加速度が加算される。上限は不明として無制限に置かれている。

## 10. 集計と貢献度計算

`RaceOperation.kt` が試行を回し、結果を集計する。

通常モードは、指定回数ぶんの `RaceSimulationResult` を集めて、全体、最大スパート成功時、失敗時の 3 つに分けて統計を出す。
グラフと詳細表示に使うフレーム列は、メモリ節約のため 1 回目の試行だけ保持する。

スキル貢献度モードは、設定を変えた複数のシミュレーションセットを走らせて平均タイムを比較する。

- 「所持していない場合」モードは、対象スキルを 1 つずつ外した設定で走らせ、基本値との差を貢献度とする。
- 「1 つ獲得した場合」モードは、対象スキルを全部外した設定を基準に、下位スキルから順に 1 つずつ足して差を取る。

いずれも、平均だけでなく上位 20 パーセントと下位 20 パーセントの平均も出し、さらに `差 * 100 / 消費スキルポイント` を効率として並べ替える。
ステータスや適性の増減も同じ枠組みで比較対象にできる。

## 11. このエミュレータで読み取れること、読み取れないこと

計算の中心は、`(速度, 体力, 位置)` の 3 変数を 15 fps で積分する常微分方程式の離散化であり、そこにスキルとイベントが状態変更として割り込む構造である。
モデル自体は素直で、ゲーム側の観測から導かれた係数表がその大半を占める。

読み取れるのは、同一コースにおける設定間の相対比較である。
スキルの発動位置とフェーズ接続、スパート成否の確率、体力の余剰、ステータス 1 段階の価値といった量は、試行回数を増やせば安定して比較できる。

一方、順位や着差は原理的に出せない。
他馬が存在しないため、順位条件のスキルは条件を満たす前提で扱われ、進路妨害は確率的な近似に置き換わり、隊列によるペース変動は仮想ペースメーカーという単純化を経る。
出力されるタイムも、位置取り争いや追い比べのように相手依存の挙動が確率で入るため、実戦の絶対値としてではなく指標として読むのが妥当である。

コード中の `FIXME` や「計算方法不明」というコメントが示すとおり、係数の一部は解析途上である。
全開スパートの速度上限、スタミナ勝負のパワー依存乱数、ブロック時の減速などは未実装または暫定値として残されている。

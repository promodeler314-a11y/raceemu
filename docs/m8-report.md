# M8 の結果

積み残しと細部の手入れをまとめて片付けた回である。
新しい機能を足したのではなく、[M4](m4-report.md) から [M7](m7-report.md) までで「次に入れる」と書いたまま残っていたものと、設計書と実装のズレを潰している。

## 1. モックと実装のズレを洗い出した

[UI 骨格のモック](../design/README.md)は設計書だけを見て起こしたもので、動いている実装と突き合わせていなかった。
両者を並べ、差分を[モックと実装のズレ](ui-gap.md)にまとめた。
モックを正とし、項目ごとに実装を寄せるのかモックを直すのかを書いてある。

途中で、体裁ではない問題が二つ出た。

- **画面にソースへのリンクが無かった。** 設計書の 2 節は「利用者がソースを取得できる状態にしておく必要がある」と書いている。AGPL v3 の下で配信する前提を満たしていなかった。フッタを置いて埋めた。
- **「基準との差」という語が二つの意味で使われていた。** モックでは保存した基準スナップショットとの差、実装ではコースの基準タイムとの差である。同じラベルで別のものを出している。

設計書の側も直した。
6.1 節の画面構成をモックに合わせ、8 節の永続化を `localStorage` から IndexedDB に改め、10 節の未決の論点を実測の出ている内容に更新した。
M3 で下した「二つの縦軸を 1 つの図に重ねない」という判断は、レポートにしか無く設計書に残っていなかったので、6.4 節として書いた。

## 2. 入力できなかった設定項目

計算モデルは前から受け取っていたのに、画面から変える口が無かったものが四つあった。
[M4 の結果](m4-report.md)の 6 節と [M5 の結果](m5-report.md)の 6 節で「次に入れる」と書いたまま残っていたものである。

- デバフの個数（15 種類）
- ポジションキープの方式と発生率
- スキル発動率の固定
- ランダム発動区間の引き

ポジションキープの `VIRTUAL` は出していない。
仮想先頭馬のステータスを入れる口が無く、選んでも `paceMaker` が `null` になって無効と同じ挙動になる。

ヒントレベルも入力できるようにした。
`cost.ts` は前から割引を計算できたが、画面から与える方法が無かったため、探索の予算計算が実態とずれていた。

共有 URL の書式は版 2 に上げた。
版 1 のリンクも読めるようにしてあり、足りない項目は既定値で埋まる。

## 3. 設定とスナップショットが消えていた

画面を閉じると比較のスナップショットが消えていた。
[M4 の結果](m4-report.md)の 6 節で「`localStorage` に置くかは M5 で決める」と書いたまま残っていた。

**IndexedDB を使う。**
スナップショットは 1 件ごとに全試行の集計とスキルごとの集計を抱えるので、`localStorage` の上限にすぐ当たる。

保存できない環境（プライベートウィンドウ、サイトデータを止めている等）では、その旨を伝えたうえでメモリ上だけで動く。
保存形式には版を持たせ、読めない版は捨てて既定値で立ち上げる。

共有 URL はハッシュから同期で読めるので、IndexedDB を待たずに先に当てる。
待つと、リンクを開いた人に既定値が一瞬見えてしまう。

## 4. Worker が死んでも誰も気付かなかった

`WorkerPool` は、Worker が「エラーを報告するメッセージ」を返した場合は扱っていたが、**返事をせずに死んだ場合を見ていなかった。**
読み込みに失敗する、例外で落ちる、メモリを使い果たす。
どれが起きても返事待ちのまま実行が終わらず、画面は「実行中」から動かなくなる。

`WorkerHandle` に `onError` を足し、落ちた Worker はプールから外して実行を失敗として終えるようにした。
落ちる Worker を差し込むテストを `parallel.test.ts` に置いてある。

実装の途中で、ハンドラを取り出す前にプールから外していたために誰にも伝わらない、という書き間違いをした。
このテストがそれを捕まえている。

あわせて失敗の見せ方を直した。

- 失敗の表示を画面の上端に一本化した。逆算と探索の失敗も同じ変数に入るのに、表示は実行パネルの中にしか無く、走らせた場所と食い違っていた。
- 壊れた共有リンクを黙って捨てるのをやめた。既定値で開くと、送った側と違う設定を見ていることに気付けない。
- 描画そのものが失敗したときの受け皿を置いた。スキルデータの読み込みは起動時に同期で走るので、そこで例外が出ると白い画面だけが残っていた。保存した設定を消して開き直す道も用意した。

## 5. ラベルとキーボード操作

先に一つ訂正しておく。
入力欄のラベルは足りていた。
`Field` が `label` で包む形になっており、`<label` の出現数だけを数えた見立てが誤りだった。

実際に足りなかったのは次である。

- 記号だけのボタンに名前が無かった。比較の `#1` と `×` は読み上げで区別が付かない。名前のないボタンが残っていないことを `pnpm e2e` で数えるようにした。
- 表の見出しに `scope` が無く、行見出しが `td` のままだった。
- 進捗の表示が読み上げの対象になっていなかった。
- キーボードから実行と中断ができなかった。Ctrl+Enter で実行、Esc で中断にした。
- タイムの分布の図に説明が無かった。

## 6. バンドル

`skills.json` のうち `info`（条件と効果の日本語の説明）、`description`、`holder` は、計算にも画面にも使われていない。
バンドルに入る段階だけで落とすようにした。
ファイル自体は本家データの写しで更新スクリプトの対象なので触らない。

| | 前 | 後 |
| --- | ---: | ---: |
| 本体 | 2.09 MB（gzip 311 kB） | 1.40 MB（gzip 218 kB） |
| Worker | 1.80 MB | 1.11 MB |

`info` は設計書 6.3 節の「近似の表示」で使う目があるので、型からは消していない。
そのときは別ファイルとして取りに行く。

減らしたものが黙って戻らないよう、`pnpm e2e` にバンドルの上限を置いた。

残る手はスキルデータの動的読み込みだが、`gameData` を同期で参照している箇所が多く、非同期化は影響が広い。
効くのは初回表示までの時間であって転送量ではないので、今回は入れていない。

## 7. 順位に関わる条件を 187 回ぶん足した

[M6 の結果](m6-report.md)の 5 節で「実装していない」と挙げた条件のうち、二つを実装した。

### 7.1 順位率の帯の維持（43 回）

`order_rate_inNN_continue` と `order_rate_outNN_continue`。
意味は「順位率の帯を、レースの開始からその時点まで一度も外れていない」と読んだ。
スキルの説明が「順位率20以前維持」と書いており、値は常に 1 で真偽として使われる。
開始からと読むのが素直で、外れる側に厳しく倒れる。

判定はフレームごとに落としていく。
一度外れたら戻らないので、外れた時点で 0 にして以降は見ない。
帯から順位の境界への対応は既存の順位率の表を引く。9 頭立てと 12 頭立ての 16 通りがすべて埋まっていることをテストで確かめた。

### 7.2 距離差（144 回）

[順位条件の扱い](order-condition.md)の 7 節で「バ身の換算を実測または既知情報で確定させる」としていた項目である。
**スキルデータの注記から確定できた。**

| 条件 | 単位 |
| --- | --- |
| `distance_diff_top` | 先頭とのバ身差 |
| `distance_diff_top_float` | 先頭との距離、0.1 m 単位 |
| `bashin_diff_infront` | 前とのバ身差 |
| `bashin_diff_behind` | 後ろとのバ身差 |
| `distance_diff_rate` | 相対位置。先頭を 0、最後方を 100 とする |

バ身は 2.5 m と読んだ。
同じ族に「先頭とのバ身差<=5」と「先頭との距離×10m<=25」の二つの書き方がある。
後者は 0.1 m 単位なので 25 は 2.5 m を指す。
float 版は 1 バ身刻みでは粗すぎる場面のために用意されたものなので、その刻み幅が 1 バ身に当たると読める。

**ゲーム内での実測はまだ取れていない。**
ここが違っていれば距離差の条件はまとめてずれるので、値は `constants.ts` の 1 か所に置いた。

### 7.3 効いていることの確認

「貴顕の使命を果たすべく」は 最終コーナー以降・コーナー・相対位置 30 以内で発動する。

| 脚質 | 判定なし | 判定あり |
| --- | ---: | ---: |
| 逃げ | 100% | 100% |
| 先行 | 100% | 95% |
| 差し | 100% | 0% |
| 追込 | 100% | 0% |

判定を入れないと距離差の条件は素通りするので、脚質によらず発動する。
入れると、先頭寄りで進む脚質だけが満たす。

先頭との距離そのものも、脚質の順に開くことを確かめた（東京 芝2400m、1200 m 地点、逃げ 0.3 バ身 / 先行 3.3 / 差し 11.0 / 追込 13.0）。

## 8. 残していること

- **順位に関わる条件のうち 122 回ぶんが未実装のまま。** 内訳はレーンに関わるもの（`infront_near_lane_time` 29、`behind_near_lane_time` 18、`is_behind_in` 16、`is_move_lane` 16、`lane_type` 12）と、周囲の頭数（`near_count` 25、`near_infront_count` 4）である。いずれも相手のレーンを持っていないと判定できない。[順位条件の扱い](order-condition.md)の 6 節に書いた限界がそのまま残っている。
- **バ身の換算と相対位置の定義の裏取り。** 7.2 節のとおり読み取りであって実測ではない。
- **モックと実装のズレ。** [一覧](ui-gap.md)の 7 節に直す順序を書いた。詳細のイベント一覧、比較の作り直し、図の色の割り当て、画面の骨格が残っている。
- **近似の表示。** 設計書 6.3 節の印はまだ無い。未実装の条件を持つスキルは探索が過大に評価するので、そのスキルに印を出す先が要る。

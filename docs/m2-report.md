# M2 の結果

[改良版の設計](webapp-design.md)の M2、並列実行と集計が終わった。
本書は、構造、実測した速度、設計から変えた点を記録する。

## 1. 構造

```
packages/sim/src/parallel/
  protocol.ts      Worker との受け渡しに使う形と、結果の詰め方
  runner.ts        1 つの塊を計算する。Worker の中でも外でも同じ関数を使う
  pool.ts          Worker を常駐させ、塊を空いた Worker へ配る
  node.ts          Node の worker_threads 用のアダプタ
  browser.ts       ブラウザの Web Worker 用のアダプタ
  bench.ts         実測用
```

Worker の実体は `WorkerHandle` という 3 つのメソッドの型で抽象化した。
Node とブラウザの違いは生成と破棄の書き方だけなので、プール側の論理は共通である。

### 設定の受け渡し

`RaceSetting` はスキルの実体を持つ。
これは条件をコンパイルしたクロージャを含むクラスなので、構造化クローンでは送れない。
そこで**スキルは ID で送り、Worker 側が自分の持つデータから引き直す**。

```ts
type SerializableRaceSetting = Omit<RaceSetting, 'skills'> & { skillIds: readonly string[] };
```

コースデータとスキルデータは Worker の起動時に一度だけ読み込む。

### 結果の受け渡し

1 試行の結果は 10 個の数値なので、塊ごとに `Float64Array` へ詰めて転送可能オブジェクトとして返す。
オブジェクトの配列を構造化クローンで送るより、確保も転送も軽い。

## 2. 設計から変えた点

[改良版の設計](webapp-design.md)では、実行のたびに Worker を立ち上げる形を想定していた。
実装してみると、これでは M7 の組み合わせ探索が成立しない。
探索は同じ設定を少しずつ変えて何千回も評価するため、Worker の起動とデータの読み込みが計算時間を上回る。

そこで **`WorkerPool` を常駐させ、`run()` を何度でも呼べる形**にした。
実測では、プールを作った直後の 1 回目と、同じプールでの 2 回目に差が出る。

| 並列数 | 初回 | 2 回目 |
| ---: | ---: | ---: |
| 4 | 6.34 秒 | 5.30 秒 |

差の約 1 秒が、Worker の起動とスキルデータ（1.7 MB）の読み込みにあたる。
探索ではこれが評価のたびに乗るはずだった。

## 3. 実測

環境は 4 コア、Node 22、tsx 経由。
1 万試行を、単一スレッドと並列で比べた。

**東京 芝2400m**

| 実行方法 | 所要時間 | 単一スレッド比 |
| --- | ---: | ---: |
| 単一スレッド | 21.24 秒 | 1.00 倍 |
| 2 並列 | 10.19 秒 | 2.08 倍 |
| 3 並列 | 7.05 秒 | 3.01 倍 |
| 4 並列 | 5.30 秒 | 4.01 倍 |

**札幌 芝1200m**

| 実行方法 | 所要時間 | 単一スレッド比 |
| --- | ---: | ---: |
| 単一スレッド | 9.60 秒 | 1.00 倍 |
| 4 並列 | 2.46 秒 | 3.91 倍 |

並列数に対してほぼ線形に伸びる。
試行が完全に独立していて共有状態が無いので、そうなるのが自然である。

### 目標との照合

[改良版の設計](webapp-design.md)の 5 節では「2000 m 級のコースで 1 万試行を数秒」を目標にしていた。
4 コアの環境で 5.30 秒、8 コアなら 2 秒台になる見込みであり、目標は満たせる。

ただしこれは Node での実測である。
ブラウザの Web Worker では、起動コストとメッセージ往復のコストが異なる。
M3 で UI を作る際に、同じ測定をブラウザ上で行って確かめる。

## 4. 確かめたこと

並列化で最も危ないのは、分割の仕方によって結果が変わることである。
乱数のストリーム分離（[M1 の結果](m1-report.md)の 2 節）によって、試行 `i` の結果はシードと `i` だけで決まる。
これが実際に守られていることを、次の 4 点で確かめた。

- **単一スレッドと 1 件ずつ完全に一致する**。400 試行を 3 並列、塊 64 で走らせ、全件のタイムが単一スレッドの結果と一致した。
- **塊の大きさを変えても結果が変わらない**。16 と 256 で一致した。
- **プールを使い回しても結果が変わらない**。間に別の設定を挟んでも、同じシードなら同じ結果が返る。
- 実測でも、並列数 2、3、4 のすべてで平均タイムが小数第 3 位まで一致した。

あわせて、進捗通知が合計と一致すること、`AbortSignal` で中断できることも確かめた。
中断は塊の境界で判定するので、既定の 256 試行なら 2400 m でも 0.5 秒ほどで止まる。

## 5. 残っていること

- **ブラウザでの実測**：`browser.ts` は書いたが、まだ動かしていない。M3 で確かめる。
- **フレーム列の記録**：並列実行では記録しない。詳細表示に使う 1 本は UI スレッドで別に走らせる想定であり、M3 で決める。
- **Worker 内のデータ更新**：スキルデータを差し替えたとき、常駐している Worker に反映する経路がまだない。M3 で必要になったら足す。

# M10 の後の方針

M10 までで入れたものを周辺のツールと並べ、次に増築するものと磨くものを選ぶための材料である。
本家 mee1080/umasim の 2026 年 9 月 11 日時点のソース、英語圏の Umalator と UmaTools、日本語の解説記事を見比べた。
出所は末尾にまとめる。

## 1. 周辺のツールがいま何を持っているか

### 1.1 本家 umasim

本家のレースエミュレータは 2025 年 11 月から 2026 年 8 月まで 2 週から 4 週ごとに版を重ねている。
v2.1.0（3 月）で全開スパート、リード確保、助走距離、賢さによる速度スキルの強化倍率、v2.1.2（4 月）でデバフ、v2.1.6（8 月）で完走率と残り体力の表示と履歴が入った。
計算側の変更は本リポジトリに移植済みである（`packages/sim/src/calculator.ts` の全開スパートとリード確保、デバフ）。

本家の画面にあって本リポジトリに無いものは次の四つである。

- **スキル貢献度モード**：所持スキルを 1 つずつ外したときの遅れ、または候補スキルを 1 つ取ったときの短縮を、平均、上振れ 20 %、下振れ 20 % の三つの値で出す。同時に「SP 効率（秒 / 100 SP）」をヒントレベル 1 から 5 までの帯で色分けする。ステータス ±100 と適性の上げ下げも同じ表に並ぶ。
- **設定のインポートとエクスポート**：キャラ名、ステータス 5 つ、適性 3 つ、スキル名をカンマ区切りで並べた 1 行の文字列である。読む側は改行、タブ、コロン、スラッシュのどれで区切っても受け、数値はステータス、`A` から `G` の 1 文字は適性、それ以外はキャラ名かスキル名として引き当てる。README の「本家がどの形式で設定を渡すのかが分かっていない」はこれで解ける。
- **SP 計算**：所持スキルの SP をヒントレベルと切れ者の有無で割り引いて合計する。本リポジトリのコストモデルは持っているが、画面には合計しか出ない。
- **MCP サーバ**：`simulate_uma_race` の 1 本で、ステータス、やる気、脚質、スキル名、回数を受けて平均と最速最遅、余剰体力、持久力温存率を返す。コースは既定値に固定で選べない。

ポジションキープの「仮想ペースメーカー」は sim には移植済みだが、画面に出していない（`apps/web/src/components/Inputs.tsx` の注記どおり、仮想先頭馬の入力口が無い）。

### 1.2 Umalator（alpha123/uma-tools 系）

英語圏で最も使われている単騎シミュレータである。
2 頭を同じ条件で走らせてバ身差の分布を出す比較が中心で、本家との違いは次の点にある。

- **Global Compare**：距離とバ場を指定すると、該当する全コースと全条件（バ場状態、天候、季節）を総当たりして集計表を出す。
- **Global Skill Chart**：コース群をまたいで、どのスキルが最も効くかを並べる。
- **ステータス配分の最適化**：焼きなまし法で、基準となる相手に対して評価点の制約内で配分を探す。目的関数は中央値、平均、集計値から選ぶ。
- **画像からの取り込みとローカル JSON の個体データベース**。
- **Electron の実行ファイル**と 1 から 16 の Worker 数の指定。

自ら「順位条件とブロックは正確でない」「脚質は後ろほど目標速度が高いので有利に出る」と断っている。
複数頭を同時に走らせる機能は無い。

### 1.3 UmaTools（daftuyda）と評価点系のサイト

UmaTools はレースを走らせない。
評価点、チーム競技場、適性試験のそれぞれを目的にしたスキル最適化、スタミナ計算、加速スキルがコースの区間に収まるかの検査、サポートデッキ、共有リンク、日英切り替え、PWA を持つ。
日本語圏の umsatei やゲームウィズの評価点シミュレータも同じく、SP あたりの評価点で並べる。

### 1.4 利用者が書いている不満

日本語の解説記事（ウマ娘スクール、うまむす速報、れが氏の note）は、本家エミュレータの限界として次を挙げる。

- 競り合い、ブロック、ポジションキープなど他のウマ娘が絡む要素が入っていない。
- 位置取り争いで体力消費が増えるので、逃げは余裕を持たせる必要がある。
- 順位条件は満たしている前提で評価される。

本リポジトリの M6 から M9 はまさにこの三つに手を付けたものである。
ただし既定で切られているなど、利用者からは見えにくい（3 節）。

## 2. 本リポジトリの立ち位置

周辺のツールと並べると、本リポジトリだけが持つものは四つある。

- **全頭を同時に走らせて勝率を出す**（M9）。本家も Umalator も単騎である。
- **目標からの逆算**（M5）。必要ステータスを分布で出すものは他に無い。
- **順位条件をフィールドで判定する**（M6、M8）。他は確率か「満たしている前提」である。
- **画像からステータス、適性、スキルをまとめて取り込む**（M10）。Umalator も持つが、日本語版の画面に合わせたものは無い。

一方で、周辺が持っていて本リポジトリに無いものは、貢献度と SP 効率（本家）、コース横断の評価と評価点の制約（Umalator）、本家形式の設定の受け渡し（本家）、AI から呼べる口（本家）である。

## 3. 増築の候補

差別化の大きさと、既にある材料でどこまで安く作れるかで並べた。
上ほど優先する。

### 3.1 チャンミの「場」をまるごと当てる

勝率の面は、相手 1 頭ごとにステータス 5 つと脚質とスキルを手で入れる。
9 頭立てなら 8 頭ぶんである。
保存した個体を当てられるが、個体はサーバのある版でしか保存できず、静的配信の版では勝率の面が実質使えない。

やることは三つに分かれる。

1. **個体のローカル保存**。`apps/web/src/individualsApi.ts` はサーバの口しか持たない。IndexedDB に同じ形で置けば静的版でも回る。サーバがあれば両方に出す。
2. **相手のプリセット**。脚質の構成（逃げ 2、先行 3、差し 3、追込 1 など）と強さの帯（ステータス合計）を選ぶと 8 頭を埋める。距離ごとに典型的な所持スキルを載せる。
3. **相手の画像取り込み**。M10 の読み取りは自分の設定にしか繋がっていない（`docs/m10-report.md` 5 節）。同じ口を相手の欄に繋ぐ。

これが揃うと、対戦相手の詳細画面を撮って並べるだけで勝率が出る。
本家にも Umalator にも無い使い方である。

### 3.2 勝率の面から 1 レースを開く

全頭同時のフレーム列は捨てている（`apps/web/src/store.ts` の `states: []`）。
単騎の結果には「分布の外れ値を押して中身を開く」があるのに、勝率の面には無い。
勝率を見た人が次に持つ問いは「なぜこの試行で負けたのか」であり、それに答える経路が無い。

着順の表から試行を選んで、全頭の位置と速度を重ねた図と、自分のスキルの発動位置を出す。
1 試行 32 ms なので、選んだ試行だけ同じシードで走らせ直せば保持する必要は無い。
本家も Umalator も単騎なので、ここも差別化になる。

### 3.3 コース横断の評価

Umalator の Global Compare にあたるものである。
距離とバ場を選ぶと該当する全コースを走らせ、コースごとの平均タイム、最大スパート率、完走率を表にする。
チャンミのコースが決まる前に候補を並べたい人と、育成中に「この個体はどのコースなら走れるか」を知りたい人が使う。

コースデータは全て持っているので、設定の配列を作って既存の Worker プールに流すだけである。
比較の面の列をコースにすれば表は作れる。

### 3.4 貢献度モードと SP 効率

本家の 1.1 節の表をそのまま持ってくる。
探索の面に「単体評価」の表はあるが、上振れと下振れ、ヒントレベルごとの SP 効率、ステータス ±100 と適性の寄与が無い。
ステータスの寄与は逆算の裏返しで、既存の `packages/solver` の評価関数で出せる。

差別化ではなく、本家から乗り換える人が「これが無い」と言う項目である。

### 3.5 本家形式のインポートとエクスポート

**入れた。** `apps/web/src/transfer.ts` と、設定の面の「本家と設定をやり取りする」である。

1.1 節の形式である。
読む側は区切りで割って値の形を見るだけ、書く側は `join(',')` である。
本家との行き来ができると、本家で作った設定を持ち込んで勝率や逆算に掛けられる。

実装して分かったことが二つある。

- **固有は名前で運べない。** 固有と継承版は名前が同じなので、名前で引くと継承版に落ちて意味が変わる。
  書き出しから固有と進化を外し、キャラ名のほうに運ばせている。読む側はキャラ名からその固有を入れる。
- **引き当てられなかった語は返す必要がある。** 黙って減ると、本家と違う結果が出たときに、
  移植の誤りなのか読み込みの取りこぼしなのかが分からない。

脚質、やる気、コース、人気、枠番はこの形式に無いので触らない。

### 3.6 AI から呼べる口

本家の MCP サーバはステータスとスキルしか受けず、コースも選べない。
本リポジトリの `apps/api` は探索、読み取り、個体の保存を持っているので、単騎の実行、勝率、逆算を JSON で受ける口を足し、その上に MCP の薄い層を置けば、本家より広い口になる。

「この個体を東京芝 2400 で走らせて、スタミナが足りないなら必要量を返して」を Claude や ChatGPT に投げられる形である。
育成を相談する使い方は本家が先に始めているが、口の広さで上回れる。

### 3.7 近似の感度分析

`docs/solver-design.md` 4 節が挙げた「近似確率を振って結果の幅を出す」である。
近似条件の確率を既定の半分と倍にして走らせ、平均タイムの幅を出す。
幅が広いスキルは近似に依存しているので、探索の結果に「この差は近似の中に消える」と添えられる。

どのツールも「100 % 正確ではない」と断るだけで、どれだけ不確かかを数字にしているものは無い。

### 3.8 評価点の制約

Umalator の最適化と UmaTools の評価点計算が持つものである。
本リポジトリは評価点を持たない。
ステータスとスキルから評価点を出す式は公開されており（ゲームウィズ）、逆算と探索に「評価点 B 以内で」の制約を足せる。
チーム競技場やオープンリーグの上限に合わせて調整する人が使う。

## 4. 既存の機能で磨くもの

### 4.1 順位条件の判定を既定で入れる

**入れた。** `store.ts` の `useField` を `true` にし、e2e の期待値を組み替えた。

ただし 1 行では済まなかった。[順位条件の判定を実戦に近づける](order-field.md)の 7 節が、
既定を入れるのは束の作り方を直したあとだと書いている。A の作り方（相手を 1 頭ずつ独立に
走らせる）のままでは、前寄りの条件が 100 %、後ろ寄りが 0 % という外れた数字を既定で
見せることになる。そこで同節の 1 番目と 2 番目（相手同士を一緒に走らせ、自分も先頭に
対して位置取りする）を先に入れ、同じ変更にまとめた。

以下は入れる前の記述である。

`store.ts` の `useField` が既定で `false` である。
M6 で入れた最大の精度改善が既定で切られており、初めて使う人は本家と同じ「順位条件は満たしている前提」の甘い評価を見る。
探索もこの設定に従うので、`docs/solver-design.md` 4 節が警告する「探索が過大評価を突く」状態が既定になっている。
M6 のレポート 7 節は「探索を回す際はフィールドを入れた状態を既定にする」と書いており、実装が追いついていない。

1 行の変更と e2e の期待値の調整で済む。

### 4.2 実行前の所要時間の見積もりと再開

**見積もりは入れた。再開は残っている。**

試行回数は 20 万まで指定でき、9 頭同時は 1 試行 32 ms なので、押してから 100 分かかる設定が作れる。
押す前に何も出ず、中断すると途中までの結果しか残らない（`docs/ui-gap.md` 8 節）。

見積もりは、条件ごとに 1 試行あたりの実時間を覚えて回数を掛ける形にした。
**「÷ Worker 数」で出す当初の案は使えなかった。** 順位条件を入れると Worker ごとに
フィールドの束（64 本）を組み直すため、本数を増やしても割り算ぶんには速くならない。
手元で測った値は次のとおりで、23 並列でも単一スレッドの 1.6 倍しか縮まない。

| 条件 | 単一スレッド | 23 並列 |
| --- | ---: | ---: |
| 単騎・順位条件なし | 1.38 ms | 0.52 ms |
| 単騎・順位条件あり | 2.22 ms | 1.37 ms |
| 9 頭同時 | 21.3 ms | 5.63 ms |

1 回も走らせていないあいだは上の表を目安として出し、走らせたら実測に置き換える。
画面には「目安」と「見込み」で書き分けてある。機種差が 1.5 倍ほどあるためである。

再開は塊が順不同で終わるので、埋まった試行番号の集合を持つ形に `WorkerPool` の受け渡しを変える。

### 4.3 探索の結果に近似の印を出す

近似条件を含むスキルの印は結果の面の発動率表にしか無い。
`docs/solver-design.md` 4 節と M8 のレポート 8 節が印の置き場として名指しているのは探索の最良構成と上位構成の表であり、そこには無い。
実行時に貯まる未対応条件の集合は CLI からしか読めず、画面には一切出ない。

全スキルを候補にする探索（`docs/server-design.md` 8 節の段取り 7）を有効にする前に、この印が要る。
印が無いまま候補を広げると、近似で過大評価されるスキルばかりが上位に並ぶ。

### 4.4 サーバ側の探索を画面から呼ぶ

`/api/search` は実装済みだが、`apps/web/src` から呼んでいる箇所が無い。
サーバ設計 8 節の残り 4 項目（並列数の実測、宛先の設定、コミット SHA の表示、全スキルの候補化）はこの経路を通してまとめて回収できる。
4.3 節の印を先に入れてから開く。

### 4.5 タブを URL に載せる

タブが経路を持たないので、ブラウザバックで面が戻らず、「探索の面」を直接共有できない（`docs/ui-gap.md` 1 節）。
共有 URL がハッシュの `#s=` を使っているので、`#tab=` を同じハッシュに同居させれば置き場の問題は解ける。

### 4.6 本家の計算式の変更を検知する

週次のワークフローが追いかけるのはスキルとコースのデータだけである。
本家は 2 週から 4 週ごとに版を出し、そのうち計算側の変更（v2.1.0 の全開スパート、v2.1.1 のクールダウン 2 秒、v2.1.3 の超常体験）はデータの取り直しでは拾えない。
本家の `race` モジュールの差分を同じワークフローで検知し、変わっていれば「計算式が動いた」と知らせる下書き PR を出す。
参照値の再生成手順（`packages/sim/test/golden/README.md`）は手動なので、これも同じ流れに載せたい。

### 4.7 UI の単体テストと lint

`apps/web/test` は純関数の 22 件だけで、929 行の `store.ts`、版を重ねながら後方互換を守る `share.ts`、IndexedDB に落ちる `persist.ts` に単体テストが無い。
ESLint も Prettier も入っていない。
共有 URL の符号化は版を増やすたびに壊れやすい場所なので、ここから足す。

### 4.8 設計書の食い違い

`docs/webapp-design.md` 1 節は「複数頭の同時シミュレーションは対象外」のまま M9 で実装され、M7 のレポート 8 節の「ヒントレベルの入力口が無い」も今は入っている。
「いま何が残っているか」の一覧として信用できるのは README の「残っていること」だけになりつつある。
本書を残課題の一覧として使い、設計書の該当箇所には本書への参照を置く。

### 4.9 モバイルの Worker 数と書体

8 コアの端末では Worker 7 本がそれぞれ 1.18 MB を読む（`docs/deploy.md` 3 節）。
上限を切るかは実機で測ってから決めるとして未着手のままである。
書体は CDN から読んでいる。

## 5. 進める順

短期（1 週間以内に効くもの）は 4.1 節の既定の切り替え、3.5 節の本家形式の受け渡し、4.2 節の見積もり表示である。
どれも既存の材料で済み、他の作業と衝突しにくい。
**この 3 つは入れた。** 4.2 節の再開は切り離して残してある。

中期は 3.1 節のチャンミの場、3.2 節の 1 レース再生、4.3 節から 4.4 節の探索の印とサーバ側の経路である。
3.1 節と 3.2 節が揃うと、勝率の面が「相手を撮って並べ、負けた試行を開く」ところまで一続きになる。

長期は 3.3 節のコース横断、3.6 節の AI から呼べる口、3.7 節の感度分析、3.8 節の評価点である。

並行して作業するときの注意として、`apps/web/src/store.ts` に全機能の状態とアクションが集まっているので、同時に触ると衝突する。
3.1 節と 3.2 節は勝率の面、3.3 節と 3.4 節は比較と探索の面と、面ごとに分けて担当するのが安全である。
